# Проверка этапа 1.5: завершения и синхронизация

Этап 1.5 завершён и принят владельцем 14.11.2026 после проверки на реальном Android.
Проверены завершение урока при недоступном Django, сохранение прогресса и операции
в SQLite, наличие pending в outbox, успешный sync после восстановления соединения
и pending = 0. OAuth, словарь,
CAS/generation закладок и SRS не входят в этот этап. Следующий шаг утверждённого
плана — **этап 2**, реальные аккаунты и защищённая доставка; шага 1.6 в плане нет.

## Сервер и dev-вход

Используются существующие PostgreSQL/Django, без новых зависимостей.
В корневом локальном `.env` задайте отдельно от Django/Admin:

```dotenv
STORYLEX_DEV_SYNC_ENABLED=true
STORYLEX_DEV_SYNC_USER_ID=<новый UUID тестового пользователя>
STORYLEX_DEV_SYNC_TOKEN=<случайный токен длиной минимум 32 символа>
```

UUID можно получить `cat /proc/sys/kernel/random/uuid`, токен —
`openssl rand -hex 32`. Храните их в локальном `.env`; не в Git, логах,
`EXPO_PUBLIC_*` или ссылках. На сервере дополнительно требуются
`DJANGO_SETTINGS_MODULE=config.settings.dev` и `DJANGO_DEBUG=true`.
При выключенном флаге, DEBUG=false или base/test-настройках dev-вход недоступен.
Флаги из клиентского JSON не включают вход и не выбирают пользователя.

Из `backend`:

```bash
uv run --env-file ../.env manage.py migrate
uv run --env-file ../.env manage.py create_dev_sync_user
uv run --env-file ../.env manage.py runserver 0.0.0.0:8000
```

Команда создаёт только настроенного non-staff User с неиспользуемым паролем,
не выдаёт права Admin, full-пакеты, Entitlement или библиотечную запись.
Используйте отдельный тестовый UUID. Адрес для телефона и Metro — по
[мобильной инструкции](mobile-development.md). Существующую опубликованную
пробу и её стабильные ID менять не нужно.

При первом запуске клиента введите токен в dev-форму. `GET /api/v1/dev/session`
с Bearer возвращает назначенный сервером `user_id`. Только после успешной
проверки клиент запоминает несекретный ID и открывает отдельную account-БД.
Токен хранится **только в памяти**; после полного перезапуска его вводят в
«Настройки → Синхронизация прогресса (dev)». Офлайн-вход в уже известный
тестовый контекст и скачанные уроки работают без токена/сети. Токен другого
пользователя отклоняется до отправки очереди. Переключение аккаунтов и настоящий
жизненный цикл access/refresh/logout остаются этапу 2.

## Хранение и протокол

- `storylex-public-v1.db` сохраняет прежние каталог, trial-пакеты, pin/ready.
- `storylex-learning-dev-v1.db` из 1.4 сохраняется без изменений. Результаты не
  копируются в аккаунт и не отправляются серверу; отметки аккаунта начинаются
  с его собственных завершений. Это не потеря старой dev-БД.
- `storylex-dev-context-v1.db` хранит только ID проверенного dev-аккаунта.
- `storylex-account-<user_id>-v1.db` имеет свои миграции: account/device/sequence,
  локальные результаты, подтверждённые состояния, outbox, cursor, last_sync.
  Account ID внутри БД проверяется при открытии; переустановка создаёт Device.
  Настройки WAL/FK/synchronous=FULL и один сериализованный writer сохранены.

Последний фактический ответ обычного урока вызывает одну транзакцию SQLite:
completion + неизменяемая команда + sequence. Итоги/100% доступны после commit.
Ошибка записи оставляет runner с повтором сохранения. Неоднозначный повтор
после commit не создаёт новую команду. Частичный урок и короткое повторение
не создают завершений/outbox. Ответы упражнений не отправляются в sync.

`POST /api/v1/sync/operations`: envelope `device_id`, 1–100 operations, максимум
256 KiB; возрастающие уникальные sequence. Реализован только `lesson.complete`
из [контракта](api-contracts.md). Для каждой команды своя транзакция:
UserSyncState lock → inbox/hash → membership опубликованного manifest → union
completion → UserChange → сохранённая квитанция. Hash включает device и всю
команду (включая время/sequence/неизвестные поля), порядок ключей JSON неважен.
Повтор возвращает прежнюю квитанцию; другой payload/device с прежним ID получает
`idempotency_key_reused`. Занятый sequence — `sequence_reused`.

Невалидные completion получают сохраняемую rejected-квитанцию; последующие
корректные команды продолжаются. Историческая опубликованная ревизия допустима
после исправления/выключения новых проб. `trial_revision` определяется сервером
по trial manifest, может быть дополнена, не стирается. UNIQUE(user, lesson)
обеспечивает union двух устройств; прогресс не удаляется. Смена availability
не даёт права скачать файлы через sync. Будущие клиентские даты ограничены
временем сервера, первое время завершения сохраняется.

`GET /api/v1/sync/changes?after=0&limit=500` фиксирует `through_cursor`;
следующие страницы передают его параметром `through_cursor`. Это номер изменения
внутри аккаунта, выделенный под блокировкой, а не PostgreSQL sequence/время.
Журнал и inbox автоматически не обрезаются. В 1.5 entity только
`lesson_completion`; state содержит product/lesson, completed=true,
trial_revision, client_completed_at, accepted_at, revision. POST не передвигает
pull cursor. Страница и cursor применяются одной SQLite-транзакцией; новая
server revision из POST не затирается старой страницей. Локальный результат и
ожидающие завершения сохраняются независимо от pull.

Один coordinator на аккаунт: отправка pending → квитанции → pull до границы.
Триггеры: запуск, локальное завершение, возврат в active, ручное действие.
Пока приложение активно, проверка выполняется раз в 30 секунд; после ошибок —
backoff с jitter до пяти минут, с учётом Retry-After. Так восстановление сети
обнаруживается без нового native-модуля. Мгновенного события NetInfo и фоновой
доставки нет. При закрытии coordinator отменяет HTTP и ждёт его завершения до
закрытия БД; отложенный ответ проверяет контекст перед commit.

Сеть, 401, 5xx, несовместимый ответ и сбой SQLite сохраняют pending. Rejected
помечается terminal, остаётся в БД и показывается в настройках по коду; локальное
завершение не удаляется. Время последнего sync записывается только после полного
pull и отсутствия pending; terminal всегда показаны отдельно, даже если время
доставки/pull обновилось. Квитанции и подтверждённые команды пока не компактируются.

## Ручная проверка Android

1. Подключите dev-сервер, войдите токеном, скачайте пробу. Проверьте ID аккаунта
   и статус sync в настройках. Результаты 1.4 остаются в отдельном хранилище.
2. Остановите Django/соединение и пройдите урок. После последнего ответа статус
   должен сохраниться до «Продолжить». В настройках есть pending и ошибка сети.
3. Полностью закройте приложение, откройте снова без Django. Урок остаётся
   завершённым, очередь сохраняется. Поздравление заново не запускается;
   короткое повторение не добавляет команду. Native force-stop в авиарежиме
   проверяйте со сборкой с доступным JS bundle: Expo Go может требовать Metro.
4. Верните Django/сеть, введите токен после перезапуска, нажмите
   «Синхронизировать». Pending станет 0, появится время успешной доставки/pull.
   Повторные нажатия и повторный запуск не создают новых LessonCompletion.
5. В Django Admin → Lesson completions (только чтение) проверьте user/lesson,
   first_revision, trial_revision, accepted_at, server_revision. Один урок —
   одна строка. Это не выдача полного права или запись библиотеки.
6. На втором устройстве войдите тем же тестовым токеном: после pull первый урок
   завершён. Завершите другой урок без сети, синхронизируйте устройства в любом
   порядке. Оба завершения должны появиться на обоих устройствах.
7. Исправьте/опубликуйте контент с теми же ID после офлайн-завершения; отправьте
   старую очередь — она должна приниматься по закреплённой исторической ревизии.
8. Введите неверный токен: отправка не проходит, уже сохранённые уроки и pending
   остаются. Верните правильный токен и повторите отправку.

Потеря HTTP-ответа после server commit, откат SQLite и истинная конкуренция
воспроизводятся автоматическими тестами; простая остановка Django не гарантирует
попадания в это узкое окно. Эти проверки не заменяют native force-stop на Android.

## Автоматические проверки

Существующие команды не менялись: из mobile `npm test`, `npm run typecheck`,
`npx expo install --check`, `npm run export:android`; из backend `uv run --env-file
../.env manage.py test --settings=config.settings.test`, `check --database default`,
`makemigrations --check --dry-run`.

Новые тесты проверяют атомарный последний ответ, ошибки диска, повторный запуск,
изоляцию прежних dev-результатов, повторы ID/sequence, исторические ревизии,
trial proof, durable rejection, 401/неподдерживаемый протокол, потерю ответа,
два клиента, устаревший pull, квитанции/курсоры при сбое, закрытый контекст,
конкурентные PostgreSQL-транзакции и миграцию с 1.4. Отдельный дочерний процесс
получает SIGKILL после последнего ответа/commit, без закрытия SQLite и без
«Продолжить»: после повторного открытия сохраняются completion и одна команда.
В агентской песочнице дочерний Node не запускался корректно; этот тест и итоговый
npm test выполнены с разрешённым запуском вне песочницы. Это проверка Node/SQLite,
не утверждение о проверенном native force-stop Android.
Django LiveServer запускает оба настоящих HTTP → SQLite теста (включая runner и
sync). В standalone npm test они явно пропускаются без адресов тестового сервера.

Повторно проверено перед коммитами 14.11.2026: 102 Django-теста (оба live-сценария выполнены), 55 мобильных тестов
(2 standalone live-теста ожидаемо пропущены), TypeScript strict, Expo module
check по локальной карте и Android JS/Hermes export. Миграции применены к
рабочей БД; Django check с БД, отсутствие миграционного дрейфа и diff check.

Ручная Android-приёмка подтверждена владельцем в объёме, указанном в начале
документа. Native force-stop, повторный запуск и два устройства не заявлены как
вручную проверенные в этой приёмке. APK-сборка здесь не выполнялась.
Expo module check в этой среде использует локальную карту версий offline;
Android JS/Hermes export не равен native-сборке. Публичный релиз по-прежнему закрыт.
Expo/Expo Go и сеть при закрытии этапа не менялись. Development build и
HTTPS-среда для авторизации отложены до следующей отдельно разрешённой задачи.
