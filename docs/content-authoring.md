# Storylex: импорт и публикация через Django Admin (этап 1.2)

Этот документ описывает 1.2 поверх 1.1; в 1.3 добавлены [публичная выдача проб](api-contracts.md)
и [мобильный каркас](mobile-development.md). OAuth, покупок и SRS пока нет.
Приведённый процесс проверяется интеграционными тестами Admin
на настоящей PostgreSQL, включая скачивание сформированных файлов.

## Обновление и запуск

Из корня проекта (существующий `.env` не заменять):

```bash
docker compose --env-file .env -f infra/compose.yaml up -d --wait db
cd backend
uv sync --locked
uv run --env-file ../.env manage.py migrate
uv run --env-file ../.env manage.py check --database default
uv run --env-file ../.env manage.py test --settings=config.settings.test
uv run --env-file ../.env manage.py runserver 127.0.0.1:8000
```

Откройте http://127.0.0.1:8000/admin/ под superuser. Для обычного staff нужны
соответствующие model permissions: изменение Product/Section для workflows,
просмотр черновиков/ревизий/артефактов для их страниц и скачивания. Импорт секции
требует также `content.change_product`. Одного `is_staff` недостаточно.

## Пример: одна полностью готовая учебная книга с одной главой

1. В **Authors** создайте автора с именами ru/en. В **Products** создайте книгу:
   `kind=book`, оба названия, автор, год, CEFR A2–B1, `access_mode=free`,
   `price_minor=0`. Для примера включите `trial_enabled` (вся единственная глава
   будет пробной). Это специально законченный короткий dev-материал, а не
   публикация недоделанной реальной книги.
2. В **Sections** создайте главу этой книги: `kind=chapter`, `position=1`,
   заголовки «Ночная прогулка» / «A Night Walk». Скопируйте UUID книги и главы
   из readonly-полей `id` в Admin.
3. Скопируйте [полный пример](../contracts/fixtures/source-chapter-v1.json)
   в свой локальный редакционный файл. Это пять единиц, 15 одиночных вопросов
   и pairs, с собственными предложениями, без цитат из произведений.
   Замените **только верхнеуровневые** `product_id` и `section_id` на UUID из Admin.
   В первом импорте одного демонстрационного Product остальные UUID примера
   можно оставить. При использовании примера для другого Product нужны новые
   учебные UUID; автоматического переназначения UUID при импорте нет.
4. Откройте главу в Admin и нажмите **«Импорт JSON»**. Выберите файл и подтвердите.
   При успехе откроется **Content drafts** с `source_hash` и `validation_version=1`.
   Это ещё не публикация. Неверный файл показывает код, русское сообщение и
   путь JSON; предыдущий черновик целиком остаётся прежним.
5. Откройте **Product** и нажмите **«Опубликовать полный материал»**. На странице
   показаны активный head, номер прежней ревизии, число новых уроков, diff
   метаданных и hashes документов, а также утверждаемые автор/серия/сериал.
   Проверьте содержание исходника и подтвердите галочкой полноту всей книги,
   смысл переводов, наличие целевой формы во всех четырёх EN-вариантах и права
   на тексты. Нажмите **«Подтвердить»**. Публикуется весь Product, не одна глава.
6. У Product появятся `current_revision` и `first_published_at`. В
   **Published revisions** откройте ревизию №1: full/trial manifests доступны
   в readonly-полях и по ссылкам **«Скачать проверенные JSON»**. В **Pack artifacts**
   откройте соответствующие full/trial записи и скачайте документы теми же
   ссылками. В **Catalog heads** проверьте ссылку на активный **Catalog revision**;
   его JSON также можно скачать. Эти ссылки требуют staff и model permission.

Для фильма «Импорт JSON» находится на самом Product, `scope=movie`,
`section_id=null`; документ содержит все уроки фильма. Для сезона импорт
выполняется на Section вида episode с `scope=episode`.

## Исправление и повторная публикация

Исправьте собственный исходный JSON, сохранив UUID и `sense_key` прежних единиц,
и повторите импорт на той же главе. Черновик сохранит собственный UUID,
действующие `PublishedRevision`, manifest, файлы и head не изменятся.
После отдельного подтверждения публикации появится новая учебная ревизия.
Опечатки/переводы можно исправлять; автоматическое определение смены смысла
невозможно, это ответственность автора. Перенос item между уроками,
переприсвоение UUID, изменение sense_key и исчезновение опубликованных UUID
отклоняются. Новые уроки имеют новые UUID; порядок существующих уроков/единиц
можно исправить без смены их идентичности.

Повтор того же JSON не создаёт новый черновик и не меняет source_revision.
Повтор публикации без изменений не создаёт ни новую учебную ревизию, ни новый
каталог/событие. Если ответ после commit потерялся, сначала проверьте active head
в Admin: повтор старого подтверждения отклоняется, не удваивает публикацию.
Подтверждение подписано и действительно час. При изменении входных данных
или head за время подготовки откройте страницу заново, проверьте diff и
подтвердите новый кандидат. Конфликт не перезаписывает чужую публикацию.

Цена/описание/автор не требуют нового пакета упражнений. Для Product, Author,
BookSeries и Show есть отдельная кнопка **«Опубликовать метаданные»**. Она меняет
только снимок каталога; у Product нельзя этим действием сменить структуру/пробу.
Изменение общего автора явно распространяется на его уже опубликованные книги
и производные authors серии. Поля других Product и их черновики не подмешиваются.
При обычной публикации Product его показанные связанные метаданные тоже
считаются утверждёнными. Автор/год серии выводятся из опубликованных детей.

## Формат, хранилище и транзакции

Источник v1: [source.schema.json](../contracts/content/v1/source.schema.json),
без изменений структуры согласованной схемы из [content-format.md](content-format.md).
Проверка UUID включена явно. Есть дополнительные смысловые проверки, которые
невозможно выразить одной JSON Schema: ссылки, уникальность по Product, целевые
сегменты, пары, соответствие перевода, стабильная идентичность и выбранный scope.
Начальный лимит — 10 MiB UTF-8 на документ; повторные JSON-ключи и NaN/Infinity
отклоняются. Редакционный `sense_key` ограничен 255 символами для индексируемого
SQL-поля. Natural-language проверку автор выполняет вручную.

UUID нормализуются в стандартную запись; исходные пробелы в текстах сохраняются.
Для hashes/файлов используется UTF-8 JSON без лишних пробелов, с сортировкой ключей
и без ASCII-экранирования Unicode. `source_hash` — hash этих канонических байтов,
не hash форматирования загруженного файла.

По умолчанию файлы находятся в **backend/.content-storage/**, каталог исключён
из Git собственным `.gitignore`. Это не MEDIA_ROOT и не static: произвольные
storage keys не доступны через HTTP. В 1.3 отдельные ID-маршруты выдают только
активированные каталоги и разрешённые trial artifacts; full-файлы по-прежнему
скачиваются только через защищённые инструменты Admin. `CONTENT_STORAGE_ROOT` можно задать
абсолютным путём окружения; при смене пути отдельно обеспечьте приватность,
исключение из Git и резервирование. Дерево:

```text
.content-storage/
  private/packs/<sha256>.json
  private/manifests/<revision-uuid>-full.json
  public/packs/<sha256>.json                 # только вырезанные пробы
  public/manifests/<revision-uuid>-trial.json
  public/catalog/<catalog-uuid>.json
```

Файлы публикуются локальным adapter через fsync и атомарную create-if-absent
ссылку; одинаковые байты переиспользуют content hash, существующий ключ никогда
не перезаписывается. Full-пакет даже бесплатного Product остаётся в private:
бесплатность не заменяет персональное право будущего API.

Все редакционные изменения в Admin и импорт увеличивают CatalogHead.source_revision
под одной блокировкой. Подготовка файлов, их чтение и проверка hashes идут вне
транзакции. Затем одна короткая транзакция проверяет прежние head/source_revision,
активную ревизию и hashes черновиков, создаёт PublishedRevision/PackArtifact,
индексы Lesson/LearningItem, CatalogRevision и переключает оба публичных указателя.
Первичная публикация/добавление уроков записывает PublicationEvent в той же
транзакции. Это только факт публикации в модуле feedback: уведомлений и обработчика
пока нет. Correction и изменения метаданных не создают «новинку».

PublishedRevision дополнительно хранит внутренние source_documents, identity_map,
content_hash и manifest_files. Это проверяемый исторический источник идентичности,
не часть публичного каталога. Реестры Lesson/LearningItem меняются только при
публикации. PostgreSQL запрещает UPDATE/DELETE immutable-строк и удаление/перенос
опубликованных учебных идентичностей; соответствие current_revision своему Product
также защищено триггером. Admin эти записи только просматривает.

## Ограничения этапа

- Полнота проверяется по всем объявленным в Admin секциям 1…N и подтверждению
  автора. Сервис не знает фактического числа глав реальной книги.
- Проба сезона разрешена только у сезона №1, эпизод №1. Проба фильма — ровно
  первые три урока; для фильма короче трёх уроков включение пробы блокируется
  до отдельного продуктового решения. Без пробы короткий фильм допустим.
- Обложки пока null, без Asset/upload: это не мешает публикации по ТЗ.
- При неудачной подготовке/конфликте возможны orphan-файлы; они не объявляются
  активным head. Автоматической уборки и UI отката нет. Старые файлы сохраняются.
- Операции записи через обычный ORM/raw SQL не заменяют редакционные сервисы
  и их source_revision. Не меняйте черновики/структуру вручную в обход Admin.
- Adapter проверяет чтение локального public namespace, а не доступность CDN.
  Object Storage, HTTP `/catalog/head`, пользовательская защищённая выдача и
  production-эксплуатация относятся к следующим разрешённым задачам.
- После commit файловая система может стать недоступна: распределённой
  транзакции PostgreSQL/storage нет. Нужны резервные копии БД и файлов вместе.
- Проверен безопасный небольшой пример; время импорта настоящей большой главы
  и работу с CDN ещё не измеряли. Новые сервисы/воркеры не добавлялись.
