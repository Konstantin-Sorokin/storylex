# Storylex: синхронизация и серверный SRS

Статус: алгоритмы на согласование. [Контракты API](api-contracts.md), [модели](data-model.md).

## 1. Локальное хранение и границы транзакций

Общий каталог/публичные пробы/обложки можно хранить в общей локальной БД. Локальный каталог хранит один полностью проверенный CatalogRevision; новый head не заменяет его до проверки файла и атомарного commit. Для персональных данных предлагается отдельная SQLite-БД на аккаунт с собственными миграциями, доступная только текущему account context. В ней: агрегированные полные права по product_id (не отдельные платёжные основания), lesson_completions с trial_revision, bookmarks, outbox, sync_cursor, report_outbox, account_settings, pack ownership и ссылки на доступные пакеты. Приватные пакеты также привязаны к account ID; физические файлы/документы не становятся доступными другому аккаунту из-за совпадения Product.

Все SQLite-записи идут через один сериализованный writer, транзакционные функции недоступны экранам напрямую. Включить FK на соединении, осознанно выбрать настройки durability и проверить аварийное закрытие на Android. Особенности async-транзакций Expo требуют проверки выбранной версии: посторонние запросы могут попасть в незавершённую транзакцию; у exclusive-варианта есть особенности отдельного соединения. Предлагается один writer/одно соединение, без конкурентных внешних запросов во время commit. Это опирается на [документацию Expo SQLite](https://docs.expo.dev/versions/latest/sdk/sqlite/), а конкретный API выбирается при реализации.

Последний ответ обычного урока выполняет **одну** транзакцию:

1. Upsert локального завершения по lesson ID.
2. Создание outbox `lesson.complete` с заранее сгенерированным UUID операции, account/device, sequence, временем и закреплённой revision ID.
3. Commit; только после успешного commit — итоговый экран и следующий доступный урок.

Если запись не удалась из-за диска, не показывать, что прогресс сохранён: сохранить экран и дать повторить запись. Сбой после commit, но до итогов не теряет завершение и не вызывает повторное поздравление после рестарта. Частичный ход урока не персистируется: после закрытия процесса он начинается сначала.

Закладка и её outbox-операция также фиксируются вместе; UI немедленно читает оптимистическую локальную проекцию. Подтверждённое состояние хранится отдельно, чтобы pull не затёр ожидающее действие.

## 2. Цикл синхронизации

1. Проверить текущий аккаунт и обновить сеанс при необходимости. Истёкший access token не блокирует уже разрешённые локальные уроки.
2. Отправить pending операции возрастающими sequence, небольшими пакетами. Для одного item сохраняется причинная цепочка. Сетевой timeout не меняет operation ID и payload.
3. Получив квитанции, в SQLite-транзакции обновить подтверждённое состояние, пометить операции acked/terminal и пересчитать оптимистическую проекцию из оставшейся очереди. Только потом можно компактировать подтверждённые записи.
4. Прочитать `/sync/changes` от сохранённого курсора до фиксированного `through_cursor`. Каждая страница и новый cursor применяются одной транзакцией.
5. Сверить catalog head, агрегированные права, задания загрузки. Сначала отправить завершения, от которых зависят закладки пробных слов; перед SRS отправить **все** ожидающие изменения словаря и разобрать конфликты. Пока завершения проб/словарь не подтверждены, соответствующие SRS не стартуют.
6. Обновить время успешного sync, когда достигнут конец изменений и нет необработанных временных ошибок учебной очереди. Конфликт отображается отдельно; он не выдаётся за успешно применённое желание пользователя.

В одном account context работает один sync coordinator. Возврат сетевого ответа после смены аккаунта не должен попасть в открытую БД другого пользователя: каждый запрос и commit проверяют захваченный account ID/session generation. Отправку останавливать на logout, персональную БД закрывать, токены удалять из активного хранилища.

Outbox не удаляется при сетевой ошибке, 401 или неподдерживаемой версии. Терминальные невалидные операции сохраняются для диагностики и видимого объяснения; они не блокируют независимые корректные завершения. Ручной sync запускает тот же процесс, не особый «сброс».

У подтверждённой локальной записи хранится собственная server revision. Старый pull или повторно полученная квитанция не могут заменить более новое состояние сущности: сравниваются её ревизии, для завершений применяется union. Общий pull cursor всё равно продвигается по всем обработанным изменениям. Это важно, когда POST уже вернул новую закладку, а последующий pull ещё читает более ранние записи журнала. Инвалидация SRS не записывает устаревший срок, а помечает онлайн-снимок требующим обновления.

## 3. Серверная идемпотентность и курсор

Каждая операция обрабатывается отдельной короткой транзакцией: блокировка UserSyncState → поиск SyncInbox по `(user, operation_id)` → проверка hash → предметная проверка → изменение состояния → запись UserChange и квитанции → commit. Для конкурирующих операций одного аккаунта получается единственный порядок. SRS, выдача права и изменение настроек используют эту же блокировку, если меняют синхронизируемое состояние. Внешние HTTP-вызовы внутри неё запрещены.

Повтор известной операции возвращает сохранённый результат без повторного эффекта. Равный ID с другим payload — ошибка. Дедупликация не опирается только на «максимальный sequence»: пропуски и частичные batch возможны. Sequence нужен для причинного порядка и диагностики; identity команды — UUID. Переустановка создаёт новую регистрацию Device.

Курсор — возрастающий **номер изменения внутри аккаунта**, выдаваемый блокированной UserSyncState в той же транзакции. Не использовать обычный PostgreSQL sequence/время обновления как watermark: порядок выделения ID не гарантирует порядок commit, и клиент может пропустить поздно закоммиченное изменение с меньшим ID.

Первый pull фиксирует верхнюю границу R. Следующие страницы читают immutable UserChange в диапазоне `(after, R]`. Новые commit > R придут в следующем цикле. В журнал попадают минимальные состояния завершений, закладок/tombstones, прав, настроек и invalidation SRS/уведомлений. Сами ответы SRS и тексты упражнений не размножаются в sync-журнале.

Для MVP журнал/квитанции не обрезаются автоматически, а новый клиент начинает с after=0. Это проще надёжного постраничного snapshot. Перед будущим pruning потребуется согласованный snapshot+epoch протокол; нельзя удалить tombstone и принять старую офлайн-команду как новую. SRS-данные после invalidation запрашиваются отдельно онлайн.

## 4. Объединение завершений

Сервер объединяет множества lesson ID операцией union. UNIQUE(user, lesson) предотвращает дубли, даже если один урок пришёл с разными operation ID. Повторное прохождение и короткое повторение не создают нового завершения.

Сервер проверяет, что lesson принадлежит Product и существовал в указанной **опубликованной** ревизии. Не требовать последнюю revision ID и не отбрасывать старое завершение после исправления JSON. Завершение не выдаёт права доступа: оно является личным заявлением клиента, не платёжным доказательством. Предлагается принимать валидные исторические завершения и после исключительного отзыва права, сохраняя прогресс, но запрещая выдачу файлов и новые закрытые SRS-вопросы. Это не позволяет получить чужой контент через sync.

Блокировка последовательности обычных уроков проверяется локально; сервер не отклоняет урок только из-за того, что предыдущий ещё не доставлен с другого устройства. Защита от искусственно нарисованного личного прогресса не усложняется: в ТЗ нет соревновательных/денежных наград за него.

Текущая завершённость главы — все lesson ID её активного manifest присутствуют в множестве. Добавление урока делает эту главу и Product неполными, но не удаляет ни одно прежнее завершение. Завершённые позже главы остаются завершёнными; следующий урок — самый ранний незавершённый доступный. Пробные и полные версии используют одни ID, поэтому покупка сохраняет пробный прогресс.

При приёме завершения сервер проверяет, включён ли lesson в trial manifest указанной content_revision_id. Если да, сохраняется `trial_revision` на LessonCompletion: это основание словаря/SRS для пяти item урока без покупки. Оно может быть дополнено при повторном завершении уже известного урока в новой пробной ревизии, не создавая второй completion. Заполнение trial_revision тоже записывается в UserChange. Исчезновение новой пробы из каталога или возврат оплаты не очищают сохранённую ссылку. Получение такого завершения не создаёт full Entitlement и не добавляет Product в библиотеку.

Завершения остаются заявлениями клиента о прохождении: проверяется реальная принадлежность урока опубликованной пробе, но сервер не доказывает каждый офлайн-ответ. Дополнительные квитанции скачивания/античит для проб не вводятся. Это тот же компромисс, что и для обычного личного прогресса; запрос закрытого item нельзя превратить в пробный одной клиентской меткой.

Для сортировки «Изучаю» используются времена фактических завершений, а не получения отложенного batch. Клиентское время не определяет разрешение конфликтов. Предлагается сохранять client time вместе с accepted_at, ограничивать будущие значения временем сервера и проверять аномалии часов; точная сортировка между неверно настроенными офлайн-часами не гарантируется.

## 5. Словарь: сравнение ревизий вместо молчаливого перезаписывания

### Правило

Принята optimistic concurrency/CAS на каждой паре `(user, item)`. Revision начинается с 0 для никогда не существовавшей записи. Каждая **смена present** увеличивает revision. Удалённый Bookmark остаётся tombstone. При absent→present создаётся новая generation UUID и чистый SRSState; present→present не сбрасывает историю. Слова завершённых бесплатных проб сохраняются теми же операциями, без full Entitlement. Сервер сначала должен принять completion этого урока; по порядку sequence оно отправляется перед bookmark.set.

Команда содержит `base.revision`, желаемый present и expected_generation. Под серверной блокировкой:

- Если база совпала, применить изменение либо noop.
- Если база устарела и обе стороны уже absent, вернуть noop: истории для удаления больше нет.
- Если база устарела и обе стороны present, noop допустим при той же expected_generation. Для двух add из отсутствующего состояния с expected_generation=NULL также допустим noop, но только если текущая revision равна base revision + 1: это один переход добавления, без промежуточного remove→add. История при noop не обнуляется.
- Иначе вернуть conflict и серверное состояние. Старое удаление никогда автоматически не удаляет повторно добавленное слово новой generation.

При несовместимых одновременных командах первой действует та, что первой зафиксирована сервером; устаревшая получает явный конфликт. Результат однозначен в едином серверном порядке и не зависит от часов устройств. Он **зависит от порядка прихода**, что является осознанным компромиссом. Удалённое давно офлайн-действие не получает права незаметно переписать более новое серверное состояние.

Это проще CRDT и безопаснее безусловного last-write-wins для удаления истории. Альтернатива «последний пришедший побеждает» убрала бы конфликтный UI, но позволила бы старому offline remove стереть недавно накопленные повторения; не рекомендуется.

### Несколько действий одного устройства до сети

Не сворачивать последовательность `remove → add` в одно `present=true`: теряется требуемый сброс истории. Первая команда содержит известную server revision; следующие ссылаются `base.operation_id` на предыдущую команду **того же item**, а expected_generation может ссылаться на её результат. Сервер разрешает ссылку из сохранённой квитанции в revision/generation и обрабатывает причинную цепочку последовательно, даже если она разделена на batch.

Если предшественник conflict/needs_confirmation/rejected, зависимая команда получает `blocked_by_conflict`, а не выполняется на произвольно перебазированном состоянии. Клиент хранит сведения о цепочке, показывает, какие изменения не применены, принимает серверную проекцию. При желании пользователь повторяет действие из актуального состояния новой командой. Независимые item/завершения продолжают синхронизацию.

### Удаление SRS-истории

Операция удаления слова с известной историей требует подтверждения пользователя; в команде передаются generation и srs_revision, относительно которых он подтвердил сброс. Сервер проверяет эти значения **даже при совпадении bookmark revision**: другой телефон мог ответить SRS, не меняя present.

Если локально истории не было, но на сервере она уже появилась, или подтверждённая SRS-ревизия изменилась, ответ — `needs_confirmation`, без удаления. После получения актуального состояния приложение просит подтвердить сброс обновлённой истории; отправляется **новая** команда с новым ID. Нельзя менять payload команды, уже получившей результат.

Успешное удаление одной транзакцией: present=false/tombstone, увеличение bookmark revision, удаление SRSState и его SRSReview, инвалидирование challenges этой generation, запись изменения/квитанции. Повтор команды не удаляет будущую историю. Повторное добавление создаёт новую generation с next_review_at=server now.

| Случай | Итог |
|---|---|
| Два устройства добавляют один отсутствовавший item | Одно слово/одно SRSState, второй add — noop |
| A удалил, B со старой базой удаляет то же | Noop при уже absent; никакой новой истории не затрагивается |
| A удалил и добавил заново; пришёл старый remove B | Conflict по generation; новая история сохранена |
| A ответил SRS; B удаляет офлайн без знания истории | Needs confirmation, слово остаётся |
| Одно устройство offline add→remove→add, исходно absent | Причинная цепочка, итог present с чистой последней generation |
| Утерян ответ на remove, затем запрос повторён | Сохранённая квитанция; нет второго эффекта |

## 6. Серверный SRS: уровни и интервалы

Предлагается трактовать `level` как **индекс интервала, который будет назначен следующим правильным ответом**. Начальный уровень 1, слово сразу due. Это устраняет неоднозначность «новый уровень 0 или 1».

| Текущий level | После верного ответа: срок | Новый level | После неверного: новый level и срок |
|---|---|---|---|
| 1 | now + 1 день | 2 | 1, now |
| 2 | now + 2 дня | 3 | 1, now |
| 3 | now + 4 дня | 4 | 1, now |
| 4 | now + 7 дней | 5 | 1, now |
| 5 | now + 10 дней | 6 | 2, now |
| 6 | now + 14 дней | 7 | 2, now |
| 7 | now + 21 день | 8 | 3, now |
| 8 | now + 30 дней | 8 | 3, now |

Продолжение после 21 дня — **предложение: 30 дней с повторением этого интервала**, без добавления SM-2/FSRS или ease factor. «Ежемесячно» здесь означает 30×24 часа, не календарный месяц. Срок считается от времени приёма ответа сервером, не от старого due или часов телефона. При ошибке слово немедленно доступно следующей выдаче, но не дублируется в уже отображаемой очереди.

## 7. Выдача очереди и обработка ответа

1. Клиент завершает отправку зависимых completion и словаря. Для summary/queue/answer действует одна проверка: present и (хотя бы одно действующее полное основание Entitlement **или** LessonCompletion.trial_revision для урока item), при отсутствии глобальной юридической блокировки. Без полного права сервер берёт вопросы **только из сохранённой пробной ревизии**; приобретение полного Product не требуется. Отключение проб для новых пользователей/возврат покупки не отзывают ранее подтверждённое пробное обучение. Среди допустимых слов выбираются next_review_at≤now по `(next_review_at, item_id)`; отдельной ночной задачи нет.
2. Выдать до 10 **разных слов**. Для каждого создать challenge с generation, state_revision, снимком вопроса, четырьмя перемешанными вариантами и TTL (предложение: 20 минут). Невыданный correct_option_id хранится на сервере.
3. Предлагаемый небольшой набор типов: W на level 1–2, R/E детерминированно чередуются по числу подтверждённых ответов на level≥3. Таким образом есть три типа, контекст присутствует, отдельной генерации вопросов не нужно. Параметры выбора не зависят от локали UI.
4. При остатке двух challenge клиент запрашивает limit=8, исключая текущие challenge/item. В очередь добавляется не более восьми новых, без промежуточного финального экрана. Ошибочное слово, уже убранное из текущей очереди, может снова попасть при refill.
5. `ready_count` — число всех **допустимых к SRS** due-слов пользователя сейчас (полное или пробное основание), включая уже выданные, но ещё не отвеченные; это не длина локальной партии. Заблокированные/закрытые слова не учитываются, nearest_review_at использует ту же проверку. В ответах возвращается calculated_at. Ошибка может оставить число прежним; устаревший badge не выдаётся за актуальный офлайн.
6. Ответ: блокировка пользовательского состояния и SRSState → проверка challenge/generation/state_revision/TTL и той же доступности слова → проверка selected_option → запись Review и нового срока/уровня → пометка challenge consumed → invalidation sync → commit. Возврат полного платежа не блокирует допустимый пробный item; удаление слова или юридическая блокировка блокируют.

Два устройства могут получить challenge одного item; первый принятый ответ увеличивает state revision, второй получает conflict без изменения срока. Глобальные блокировки очередей/длинные аренды не нужны. Повтор того же answer ID и того же выбора по consumed challenge возвращает принятый результат, пока receipt хранится. Другое тело с тем же ID или второй answer ID для того же challenge не создают нового Review.

После удаления слова старые challenge дают gone, а не восстанавливают состояние из сохранённого ответа. Можно сохранить короткоживущую техническую отметку consumed/invalidated без истории интервальных сроков; сброшенные Review удаляются. По истечении TTL неизвестный/очищенный challenge отвергается, никогда не переисполняется.

При потере сети текущая карточка приостанавливается. Ответ не сохраняется в постоянный outbox; незавершённый HTTP может повториться с тем же ID **после восстановления сети в текущем сеансе**. До выяснения результата не переходить к следующему вопросу. Если процесс завершился, клиент обновляет summary/queue с сервера; уже принятые ответы сохранены. Это обработка неопределённого результата HTTP, а не офлайн-SRS.

## 8. Локальное напоминание и наблюдаемость

Напоминание — одно локальное уведомление в день в выбранное время (предложение 19:00), без обещания точного числа due-слов и без серверного push. Разрешение спрашивается только после согласия в объясняющем диалоге при первом добавлении. Отказ сохраняется, автоматическое повторное предложение не делается. При смене часового пояса/времени и после logout расписание сверяется с текущим аккаунтом.

Предлагаемый порог проблемы sync: очередь старше 24 часов **и** неудачная попытка при фактически доступном API; обычный длительный авиарежим сам по себе не ошибка. На карточках пакетов — отдельное состояние загрузки. В настройках видны время последней успешной синхронизации и ручной запуск. Необходимы серверные метрики: возраст pending платежей, ошибки sync, конфликты, ошибки публикации; без словарных текстов и токенов в логах.
