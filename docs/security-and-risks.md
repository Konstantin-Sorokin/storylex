# Storylex: безопасность, противоречия и риски

Статус: предложения и перечень проверок; юридическая допустимость коммерческой схемы **не подтверждена** этим проектом. [Архитектура](architecture.md), [план](implementation-plan.md).

## 1. Вход и управление аккаунтом

Для первой публичной Android-сборки обязательны Google и Яндекс ID. Предлагается OAuth/OIDC через системный браузер, серверный callback и одноразовый ticket, привязанный к доказательству владения запросом на устройстве. Сервер применяет проверку `state`, одноразовость попытки, allowlist callback/return URI, PKCE/nonce там, где это поддерживается конкретным flow, и проверку внешней identity по протоколу провайдера.

Не считать произвольный переданный `provider_user_id` или email доказательством входа. Для OIDC проверяются подпись, issuer, audience, срок и nonce; для OAuth — проверенные token/userinfo ответы провайдера. Client secret остаётся только на сервере. Provider-specific adapters небольшие, а не универсальная самописная OAuth-платформа; подходящую поддерживаемую библиотеку выбрать в техническом spike без изменения архитектурных границ.

Expo рекомендует development build для проверки OAuth redirect; Expo Go не даёт нужной настройки схемы возврата. Поддержка PKCE и тип клиента зависят от провайдера, поэтому единый flow нельзя считать проверенным заранее. См. [Expo: authentication](https://docs.expo.dev/guides/authentication/). На spike проверяются реальные Google/Яндекс регистрации, требования типа OAuth-клиента, браузерный возврат и Android без предположения об обязательном наличии Google Play Services.

Собственные access tokens предлагаются короткими JWT (15 минут), refresh — случайными непрозрачными (30 дней) с хешем на сервере, ротацией и отзывом. Это предложенные начальные сроки. Access — в памяти, refresh — в защищённом хранилище ОС через SecureStore, не SQLite/AsyncStorage/логи. JWT проверяется по подписи/iss/aud/exp и серверной активности сеанса, чтобы logout/delete/revoke имели действие до истечения JWT. Повтор refresh после потери ответа должен распознаваться по request_id в коротком безопасном окне; не хранить открытый refresh для этого в обычной БД.

Привязка нового провайдера требует активной собственной сессии и отдельного подтверждённого входа в новый provider. Совпадение email ничего не объединяет. Уже связанная с другим User identity даёт конфликт; слияние аккаунтов не входит в MVP. Нельзя отвязать последний способ входа. Удаление аккаунта требует недавней повторной авторизации и явного подтверждения, не выполняется офлайн.

Админка — отдельный ограниченный staff-доступ по HTTPS, с сильной аутентификацией и защитой от перебора; требование «нет пользовательских паролей» относится к мобильным аккаунтам, не запрещает административный механизм Django. Тестовый API требует staff и отдельного preview окружения; одного скрытия кнопки недостаточно.

## 2. Офлайн-доступ и защита пакетов

Полные пакеты хранятся в **непубличном bucket**. Публичный bucket содержит каталог, обложки и вырезанные пробные документы, не исходные полные главы с флагом `locked`. Облачные ключи есть только у backend; публичные листинги приватного пространства закрыты.

Сервис выдачи сопоставляет artifact→revision→Product, проверяет агрегированное полное право (есть хотя бы одно действующее основание Entitlement) и availability, затем создаёт подписанный GET URL с предложенным TTL 5 минут. Пробные артефакты доставляются отдельно по разрешённому trial manifest, не открывая полный пакет. Знание UUID или object_key само по себе не даёт полного доступа. Возможность ограниченной во времени выдачи предусмотрена [Yandex Object Storage](https://yandex.cloud/en/docs/storage/concepts/pre-signed-urls). Подписанный URL — временный bearer-доступ: не писать query string в analytics/crash logs, не включать его в общий кеш.

Целостность JSON проверяется относительно hash доверенного manifest. Для HTTPS нужны обычная проверка сертификатов и актуальный системный trust store, без самодельного отключения TLS-проверок. Шифрование контента собственными встроенными ключами не предлагается как DRM.

На устройстве платные документы и их права изолированы по account context и находятся в приватной области приложения. После logout файлы остаются, но открыть их можно только после входа соответствующего аккаунта и восстановления его локального контекста. Токен, истёкший во время офлайна, не лишает владельца уже доступных уроков. Новое право офлайн не появляется; смена бесплатной цены на платную не отменяет выданное бесплатное право.

Юридическая availability-блокировка немедленно запрещает новую выдачу и SRS на сервере независимо от источника права, включая пробы; локальное открытие блокируется после получения обновлённого каталога/серверного запрета. Пока каталог не доставлен, мгновенный отзыв локальной копии не гарантируется даже при наличии сети. Возврат платежа/отзыв одного основания действует иначе: полная выдача прекращается только при отсутствии других действующих оснований; SRS слов завершённой пробы остаётся доступен без покупки. Предлагается не вводить срок обязательной онлайн-проверки для уже скачанного материала. Следствие: невозможно немедленно отозвать доступ у устройства, остающегося офлайн, или стереть извлечённую копию. Уже выданный подписанный URL может работать до expiry. Если понадобится строгая offline lease, это изменит продуктовый компромисс и потребует отдельного согласования.

Пробный SRS опирается на подтверждённый completion и его trial_revision. Сервер проверяет membership item в этом пробном снимке, использует только его вопросы, не доверяет клиентской метке `is_trial` и не требует full Entitlement. Отключение новых проб не удаляет уже подтверждённое пробное обучение. Сохранение такого слова не создаёт полного права, записи библиотеки или подписки на новинки.

## 3. Заказы, платежи и возвраты

ЮKassa остаётся предполагаемым провайдером согласно ТЗ. Перед коммерческой реализацией подтвердить допустимый для RuStore способ продажи цифровых учебных материалов, роль магазина, форму оплаты, возвраты и чеки. Здесь не делается вывод о действующих правилах площадки. Проверка конкретной схемы — gate коммерческого этапа, а не причина откладывать импорт и уроки.

Предлагаемый жизненный цикл:

1. Backend сериализует операции user/Product через UserSyncState, проверяет агрегированное полное право и существующий creating/pending заказ. Сумма/режим берутся из текущего активного CatalogRevision и фиксируются в заказе; изменяемые draft-поля и старый каталог телефона не являются ценой продажи.
2. Заказ и стабильный provider idempotency key сохраняются **до** создания платежа. Внешний запрос выполняется вне длительной БД-транзакции. При timeout команда сверки повторяет создание с тем же ключом, не создаёт второй платёж.
3. Приложение открывает согласованную платёжную форму. При возврате вызывает backend refresh и автоматически наблюдает pending, не выдавая себе доступ по URL.
4. Webhook используется как сигнал. Backend сверяет платёж у провайдера с секретным серверным доступом: объект, merchant/account контекст, сумму/валюту, статус и связь с заказом. Не выдумывать обязательную HMAC-подпись, которой у выбранной интеграции может не быть. Официальная [документация ЮKassa](https://yookassa.ru/developers/using-api/webhooks) описывает проверку по статусу объекта и/или адресу источника; предлагается всегда проверять объект через API, IP-фильтр — дополнительный слой.
5. В короткой транзакции фиксируются проверенное successful состояние и не более одного **purchase-основания на order**, затем пересчитывается агрегат права и пишется UserChange. Уже имеющееся free-основание не заменяется и не отзывается. Повторы webhook/polling безопасны за счёт UNIQUE(order) и проверки состояния. Платёжный endpoint подтверждает приём лишь после надёжного сохранения обработки; входящее уведомление не считается оплатой само по себе.
6. Management command периодически сверяет зависшие заказы и необработанные уведомления. При проверке статуса нельзя вернуть успешный платёж в pending из-за старого webhook. До подтверждения отмены нельзя разрешить новую оплату того же заказа.

Возвраты имеют отдельные записи, проверяются у провайдера и отражаются идемпотентно. Полный возврат (включая сумму нескольких подтверждённых частичных) отзывает только Entitlement с order этого платежа. Агрегат `has_full_access = EXISTS(действующее основание)` пересчитывается в той же транзакции; бесплатное/другое основание остаётся. Частичный возврат до полной суммы не отзывает основание автоматически; юридические исключения — ручная согласованная процедура. Старое successful уведомление не возрождает отозванное основание/заказ refunded. Если refund получен раньше локальной обработки successful, сначала сверяются платёж и сумма возвратов: активное основание полностью возвращённого платежа не выдаётся даже временно.

Для MVP новая покупка уже доступного Product запрещена. Однако pending-платёж может завершиться после независимого claim-free: проверенный платёж не теряется, сохраняются два основания. При возврате покупного бесплатное продолжает действовать. `claim-free` создаёт/возвращает отдельное free-основание по текущему активному режиму; повтор команды не дублирует его. Записи источников не выводятся как пользовательская история покупок. Отдельной таблицы агрегатов и универсальной биллинговой системы не требуется.

| Основания | Событие | Итог |
|---|---|---|
| Только purchase A | Полный возврат A | Полное право false; SRS допустимых пробных слов сохраняется |
| Purchase A + free | Полный возврат A, в том числе повтор webhook | Полное право true за счёт free; одна запись в библиотеке |
| Purchase A + purchase B (проверенные разные заказы) | Возврат A | Основание B сохраняется; такое сочетание не разрешает намеренно создавать повторную оплату |
| Free | Материал снова платный | Бессрочное полное право сохраняется |
| Подтверждённая проба, полного основания нет | Bookmark/SRS | Разрешены только слова завершённых пробных уроков; full manifest запрещён |

При удалении аккаунта отменяются сеансы и личные данные, но удаление/обезличивание платежных записей определяется обязательствами хранения. Предупреждение о последствиях восстановления покупок показывается до удаления. Не обещать восстановить удалённый аккаунт по совпавшему email.

## 4. Dev-изоляция и минимальная эксплуатация

- Public и dev/preview — разные сборки и окружения данных. Preview использует отдельный SQLite namespace, тестовые права и прогресс; сброс доступен только там. Dev-заглушка не может включиться по удалённому параметру публичной сборки.
- Приватные API фильтруют QuerySet по user; чужие order/report/challenge/device ID не обходят ownership-проверку. Account ID из запроса не доверенный.
- Rate limits на вход, refresh, подпись URL, batch sync, SRS и платежи; лимиты размера JSON/комментариев; Admin-import не выполняет код из файла. Обычные упражнения содержат plain text/структурированные сегменты, не HTML.
- Структурированные серверные логи содержат request_id и безопасные коды операций. OAuth code, access/refresh, платёжные секреты, подписанные URL и полный словарь исключаются. Crash reporting отдельно от переключателя аналитики.
- Обязательные резервные копии PostgreSQL, исходных JSON и настроек/ключей восстановления; опубликованные артефакты также резервируются либо проверенно воспроизводятся из сохранённых источников и manifest. Предлагаемый старт: ежедневная копия БД, хранение 30 дней, регулярная проверка восстановления; целевые RPO 24 часа/RTO один рабочий день требуют утверждения до платного запуска.
- Новинки создаются повторяемой командой из PublicationEvent. Ошибка команды не теряет публикацию; ключ UNIQUE(user,event) предотвращает дубли. Системные push о новинках не нужны.

## 5. Противоречия и недостаточно определённые места ТЗ

Здесь собраны конкретные развилки. Ни одна не заменяет подтверждённое требование молча.

| Место ТЗ | Неоднозначность / риск | Рекомендация и последствия |
|---|---|---|
| §15.4 «не сбрасывает ранее завершённые главы» против §7.1, §8.1, сценария 11 | Новые уроки в старой главе одновременно должны сделать её неполной | Сохранить все lesson completions; текущую завершённость **изменённой** главы пересчитать. Другие главы не затрагиваются. Буквальное «глава навсегда завершена» противоречило бы приёмке |
| §18.1 редактирование уроков в Admin и §18.2–18.3 исходный JSON | Два редактируемых источника вопросов разойдутся | Admin редактирует каталог/структуру и загружает целую главу; вопросы правятся только JSON. Отдельный редактор упражнений не нужен |
| §3 полная готовность единицы и §7/§19 новые уроки | Нельзя использовать обновления как оправдание продажи недоделанной книги | Первичная публикация проверяет весь объявленный состав. Позднее допустимы отдельные расширения/исправления с явным diff и сохранением ID |

| §13–15 офлайн-удаление против новой SRS-истории другого устройства | Локальное «истории нет» может уже быть неверным | CAS + generation + проверка srs_revision; запросить повторное подтверждение, не удалять молча |
| §14 уровни и интервалы | Не определён индекс уровня и интервалы после 21 дня | Level — индекс следующего верного интервала; 1/2/4/7/10/14/21/30, затем 30. Подробная таблица в SRS-документе |
| §10.1 управляемая случайность против §10.5 стабильного порядка | Перезапуск не должен превращать порядок в иной алгоритм | Детерминированный шаблон и seed lesson ID; каждый показ случайно переставляет варианты. Seed/планировщик версионируются |
| §10.4 полоса без отката при 16–21 задании | Точный визуальный алгоритм пока не выбран | **Отложено владельцем до реализации lesson runner.** Формула, веса и резерв процентов не фиксируются. Проверяются отсутствие отката, учёт пар как одного задания и 100% только в конце |
| §16.1 проба фильма «три урока» | В ТЗ нет минимальной длины фильма | Предлагается отклонять trial_enabled у фильма с <3 уроками; альтернатива min(3,N) делает короткий платный фильм целиком пробным. Решить до публикации такого материала |
| §16.1 проба сериала | Можно ошибочно включить пробу каждого сезона | Разрешать только эпизод №1 сезона №1. Не подменять его первым опубликованным сезоном, если сезон №1 отсутствует |
| §13–14 и §16.1 пробные слова | Проверка только full Entitlement ошибочно блокировала бы словарь/SRS пробы | Явно разрешены слова завершённых пробных уроков: trial_revision у completion, вопросы только пробного снимка, без покупки и без библиотечной записи |
| Каталог/цены и /catalog/head | Активация номера в БД до загрузки статического файла давала несогласованный head | Файл и все зависимости готовы до атомарного переключения CatalogHead/публичных ревизий; conditional activation защищает от конкуренции. После активации outage storage всё ещё возможен |
| Entitlement и возвраты | UNIQUE(user, product) не выражал несколько оснований | UNIQUE только для free-пары, UNIQUE(order) для purchase; итог через EXISTS, в API/sync агрегат один на Product. Возврат отзывает только свой order |
| Автор и год книжной серии | У разных томов могут отличаться авторы/годы | Author.name_ru/en на книге; у серии производные authors и min(year) опубликованных томов. Это не отдельная дата начала всей серии; её значение может меняться с составом каталога |
| §6 все обложки/пробы при подготовке | Неограниченный каталог увеличивает первый запуск и расход сети | Выполнить требование, ограничив параллелизм, размер обложек и сохраняя checklist. Рекомендация: частичный сбой некритичной обложки не блокирует уже рабочие уроки. Выбор metered-network политики и условия окончания подготовки — до UX-приёмки |
| §5 офлайн после expiry и §16 исключительный отзыв | Немедленный отзыв на офлайн-устройстве недостижим | Применять отзыв после соединения; без offline lease. Не обещать DRM или мгновенное удаление копий |
| §7.1 последнее завершённое действие | Неясно, меняют ли порядок короткое повторение и SRS | Предлагается сортировать по обычным завершениям; повторения отдельно не двигают произведение. Иначе нужен ещё один вид учебного события, не влияющий на completion |
| §19 приобретённое и бесплатно полученное | Формулировка «приобрёл книгу» может исключить бесплатное право | Учитывать все постоянные entitlement, включая free; проба не создаёт подписку на новинки. Граница — granted_at раньше публикации |
| §20 аналитика по умолчанию и право на данные | Настройка по умолчанию не доказывает законность сбора | До выпуска проверить согласие/политику/SDK. Не собирать события до решения коммерческого privacy gate |
| §5 удаление аккаунта и §17 платежи | Нельзя заранее обещать физическое удаление всех финансовых сведений | Согласовать retention/обезличивание отдельно, предупредить о потере персонального прогресса и последствиях для покупок |

## 6. Технические риски и проверка

| Риск | Как снять неопределённость |
|---|---|
| Object Storage недоступен после успешной активации | Проверять файл до переключения, не менять immutable ключи; при последующем сбое сохранять старый локальный каталог/пакет и повторять. Распределённая транзакция не вводится |

| Многодневный offline и повторная отправка | Стабильные ID, tombstones, immutable receipts; тест двух независимых локальных БД и сервера |
| Работа OAuth/платежей из целевой сети | Проверить на реальных Android-устройствах/сетях; не подменять обязательных провайдеров без согласования |
| Долгий импорт/публикация | Измерить настоящую главу; сначала лимиты/оптимизация, worker добавлять только при доказанной необходимости |
| Рост журнала и артефактов | Метрики объёма, отсутствие преждевременной чистки; будущий retention только с snapshot/migration протоколом |
| Уведомления новых публикаций при сбое | Транзакционный PublicationEvent и повторяемая обработка с уникальностью |
