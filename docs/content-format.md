# Storylex: JSON, публикация и локальные пакеты

Статус: предложение на согласование. [Модели](data-model.md), [API](api-contracts.md).

## 1. Единицы импорта и доставки

**Импорт:** один полный документ на главу книги / эпизод сезона; для фильма — один документ со всеми уроками. Автор выбирает соответствующую единицу в Admin, ID документа обязан совпасть с выбором. Источник упражнений — этот редактируемый JSON, а не форма каждого вопроса в Admin.

**Публикация:** одна целостная ревизия Product (книга, сезон, фильм). Она ссылается на неизменяемые документы всех глав/эпизодов или фильма. Новый импорт одной главы не публикует её немедленно и не делает незавершённую книгу публичной.

**Доставка:** полный пакет — manifest и все перечисленные в нём документы. Не нужен большой ZIP: клиент автоматически скачивает все части, переиспользуя неизменившиеся по SHA-256, и активирует весь новый manifest разом. Это сохраняет требование «приобретённый материал скачивается целиком», но не заставляет повторно передавать книгу после исправления одной главы. Пробный manifest содержит только разрешённую часть и не ссылается на платные упражнения.

## 2. Идентичность и версии

| Поле | Назначение |
|---|---|
| `schema_version` | Целочисленная версия формата JSON; v1 — предлагаемая ниже |
| `product_id`, `section_id` | Стабильные UUID каталога, не название и не порядковый номер |
| `lesson.id`, `item.id` | Стабильные UUID для прогресса и словаря |
| `sense_key` | Редакционный ключ значения внутри Product, например `carry-out.perform` |
| `exercise.id`, `option.id`, `pairs.id` | UUID для жалоб, ответов и сохранения идентичности при исправлениях |
| `revision_id`, `revision_number` | Серверные UUID/номер опубликованного снимка Product; в исходнике не задаются |
| `sha256`, `byte_size` | Целостность конкретного артефакта; не версия предметной сущности |

Номер урока или положение в JSON не входят в идентификатор. Исправление опечатки/перевода при том же значении сохраняет item/lesson/exercise ID. Замена значения, перенос учебной единицы в другой урок, расщепление или слияние опубликованного урока не выполняются автоматически: импорт отклоняется и требует отдельного решения о миграции. MVP поддерживает исправления и добавление новых уроков с новыми ID. Чужие UUID и переиспользование удалённого ID для другого содержания запрещены.

`sense_key` предотвращает дубли в пределах книги/сезона/фильма. Равенство значений естественного языка всё равно проверяет автор: валидатор не распознаёт синонимы. Одинаковые строки в разных Product имеют разные item ID и независимые словарь/SRS-истории — это принято владельцем. Общий лингвистический словарь и автоматическое слияние не вводятся.

Новая несовместимая схема требует обновления приложения. Клиент с неподдерживаемой схемой сохраняет прежний рабочий пакет и сообщает о необходимости обновления, не очищая прогресс.

## 3. Формальная структура исходного документа v1

Ниже **проект JSON Schema**, помещённый в Markdown для обсуждения, не созданный контрактный файл. При реализации валидатор должен проверять `format: uuid`; одной аннотации `format` недостаточно. Правила между объектами дополняют схему в следующем разделе.

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "Storylex source content v1",
  "type": "object",
  "additionalProperties": false,
  "required": ["schema_version", "product_id", "scope", "section_id", "title", "lessons"],
  "properties": {
    "schema_version": { "const": 1 },
    "product_id": { "$ref": "#/$defs/id" },
    "scope": { "enum": ["chapter", "episode", "movie"] },
    "section_id": { "type": ["string", "null"], "format": "uuid" },
    "title": { "$ref": "#/$defs/localized" },
    "lessons": {
      "type": "array", "minItems": 1,
      "items": { "$ref": "#/$defs/lesson" }
    }
  },
  "$defs": {
    "id": { "type": "string", "format": "uuid" },
    "text": { "type": "string", "minLength": 1 },
    "localized": {
      "type": "object", "additionalProperties": false,
      "required": ["ru", "en"],
      "properties": {
        "ru": { "$ref": "#/$defs/text" },
        "en": { "$ref": "#/$defs/text" }
      }
    },
    "segment": {
      "type": "object", "additionalProperties": false,
      "required": ["text", "target"],
      "properties": {
        "text": { "$ref": "#/$defs/text" },
        "target": { "type": "boolean" }
      }
    },
    "richText": {
      "type": "array", "minItems": 1,
      "items": { "$ref": "#/$defs/segment" }
    },
    "example": {
      "type": "object", "additionalProperties": false,
      "required": ["en", "ru"],
      "properties": {
        "en": { "$ref": "#/$defs/richText" },
        "ru": { "$ref": "#/$defs/richText" }
      }
    },
    "option": {
      "type": "object", "additionalProperties": false,
      "required": ["id", "text"],
      "properties": {
        "id": { "$ref": "#/$defs/id" },
        "text": { "$ref": "#/$defs/text" }
      }
    },
    "question": {
      "type": "object", "additionalProperties": false,
      "required": ["id", "prompt", "options", "correct_option_id"],
      "properties": {
        "id": { "$ref": "#/$defs/id" },
        "prompt": { "$ref": "#/$defs/text" },
        "options": {
          "type": "array", "minItems": 4, "maxItems": 4,
          "items": { "$ref": "#/$defs/option" }
        },
        "correct_option_id": { "$ref": "#/$defs/id" }
      }
    },
    "exercises": {
      "type": "object", "additionalProperties": false,
      "required": ["word_to_translation", "context_ru_to_en", "context_en_to_ru"],
      "properties": {
        "word_to_translation": { "$ref": "#/$defs/question" },
        "context_ru_to_en": { "$ref": "#/$defs/question" },
        "context_en_to_ru": { "$ref": "#/$defs/question" }
      }
    },
    "item": {
      "type": "object", "additionalProperties": false,
      "required": ["id", "sense_key", "kind", "en", "ru", "example", "exercises"],
      "properties": {
        "id": { "$ref": "#/$defs/id" },
        "sense_key": { "$ref": "#/$defs/text" },
        "kind": { "enum": ["word", "phrasal_verb", "expression", "grammar"] },
        "en": { "$ref": "#/$defs/text" },
        "ru": { "$ref": "#/$defs/text" },
        "example": { "$ref": "#/$defs/example" },
        "exercises": { "$ref": "#/$defs/exercises" }
      }
    },
    "lesson": {
      "type": "object", "additionalProperties": false,
      "required": ["id", "position", "items", "pairs"],
      "properties": {
        "id": { "$ref": "#/$defs/id" },
        "position": { "type": "integer", "minimum": 1 },
        "items": {
          "type": "array", "minItems": 5, "maxItems": 5,
          "items": { "$ref": "#/$defs/item" }
        },
        "pairs": {
          "type": "object", "additionalProperties": false,
          "required": ["id"],
          "properties": { "id": { "$ref": "#/$defs/id" } }
        }
      }
    }
  }
}
```

`items` идут в порядке первого появления значений. Каждая единица содержит три вопроса; пары строятся по пяти `item.id → en/ru`, отдельный дублирующий список переводов не хранится. Итого строго `5 × 3 + 1 = 16` базовых заданий. Массив дополнительных упражнений в JSON не нужен: они повторно используют соответствующий ошибочный вопрос с новой перестановкой вариантов.

`scope=movie` требует section_id NULL; глава/эпизод — существующий section_id правильного вида. Локализуются заголовки/метаданные, не ключи типов и не учебные EN/RU тексты. В полях нет CEFR отдельных слов, цитат из книги, озвучки или изображений заданий.

### Пример части учебной единицы

Это **фрагмент**, а не импортируемый урок: идентификаторы для удобства сокращены, два остальных обязательных вопроса и ещё четыре единицы здесь не повторяются.

```json
{
  "id": "item-uuid",
  "sense_key": "carry-out.perform",
  "kind": "phrasal_verb",
  "en": "carry out",
  "ru": "выполнять",
  "example": {
    "en": [
      { "text": "We will ", "target": false },
      { "text": "carry out", "target": true },
      { "text": " the plan tomorrow.", "target": false }
    ],
    "ru": [
      { "text": "Мы ", "target": false },
      { "text": "выполним", "target": true },
      { "text": " план завтра.", "target": false }
    ]
  },
  "exercises": {
    "word_to_translation": {
      "id": "exercise-uuid",
      "prompt": "carry out",
      "options": [
        { "id": "option-a-uuid", "text": "выполнять" },
        { "id": "option-b-uuid", "text": "откладывать" },
        { "id": "option-c-uuid", "text": "отменять" },
        { "id": "option-d-uuid", "text": "обсуждать" }
      ],
      "correct_option_id": "option-a-uuid"
    }
  }
}
```

Сегменты позволяют выделять целевой фрагмент в обоих языках **после ответа**, без HTML, Markdown-парсера и ошибок с Unicode-offset. До ответа вопрос/варианты отображаются обычным текстом. В контекстных заданиях дополнительное объяснение не показывается.

## 4. Проверки импорта сверх JSON Schema

1. Проверить UTF-8, размер документа, допустимые поля и версию схемы. Предлагаемый начальный предел — 10 MiB на документ; это технический лимит, уточняемый на реальной главе.
2. Проверить product/section/scope, позиции уроков 1…N без пропусков и повторов, пять единиц, три вопроса на единицу и единственный pairs ID.
3. Проверить уникальность всех ID в своей области и отсутствие коллизий с чужим контентом. `correct_option_id` ссылается ровно на один из четырёх разных option ID. Нормализованные тексты вариантов не совпадают.
4. `word_to_translation.prompt = item.en`, правильный ответ соответствует item.ru. В парном задании английские и русские подписи должны однозначно различаться; иначе редакционный отчёт, а не угадывание соответствия одинаковых переводов.
5. В примере есть target-сегмент в каждом языке. Для контекстных вопросов проверяются наличие текстов и язык по структуре; естественный язык, правильность смысла и присутствие нужной грамматической формы во всех четырёх EN-предложениях подтверждает автор, не ненадёжный поиск подстроки.
6. Проверить `sense_key` по всему Product, включая неизменённые главы; обновление того же item не считается дублем. Сравнить с опубликованной идентичностью; исчезновение/перенос/замена старых уроков отклоняются в MVP.
7. Только после полной проверки заменить ContentDraft в одной транзакции. При ошибке нет частичного импорта; отчёт содержит код, локализованное сообщение и путь вроде `/lessons/2/items/4/exercises/context_ru_to_en/options`.

## 5. Планировщик обычного урока

Предлагается версионированный алгоритм `lesson_engine_version=1` в опубликованном manifest. Он формирует один и тот же порядок вопросов для lesson ID и ревизии, варианты ответов перемешиваются при каждом показе независимо.

Обозначения: `W` — слово→перевод, `R` — RU→EN контекст, `E` — EN→RU контекст. Для пяти индексов, назначенных детерминированной перестановкой по lesson ID, допустим шаблон:

```text
W1 W2 R1 W3 R2 W4 R3 W5 R4 E1 R5 E2 PAIRS E3 E4 E5
```

Он обеспечивает первую встречу типа W, отсутствие соседних одиночных вопросов одного item, пары на позиции 13 и контекстный финал. Список слов на итогах всегда остаётся в исходном порядке, независимо от перестановки планировщика. Это конкретное предложение трактовки «управляемого перемешивания», а не уже утверждённое правило ТЗ.

После базы — по одному вопросу на item с ошибками, максимум пять. Предлагаемый приоритет сложности: R > E > W; ошибки пар исключены. Дополнительная ошибка не порождает новую цепочку. Короткое повторение — пять вопросов, случайно R или E на каждый item, без отработки и без SRS.

**Точный алгоритм визуального заполнения прогресс-бара отложен до реализации lesson runner.** Архитектура не фиксирует формулу, резерв процентов или веса заданий. Сохраняются требования ТЗ: отсутствие отката, 100% только после последнего фактического задания, пары считаются одним заданием, всего 16–21. Это поведение проверяется на lesson runner и не требует поля/формулы в учебном JSON или REST API.

## 6. Публикация и manifest

Предлагаемый manifest одной приобретаемой единицы (ID/хеши сокращены, пример не является валидным артефактом):

```json
{
  "schema_version": 1,
  "lesson_engine_version": 1,
  "product_id": "product-uuid",
  "revision_id": "revision-uuid",
  "revision_number": 3,
  "scope": "full",
  "counts": { "sections": 2, "lessons": 4, "items": 20 },
  "documents": [
    {
      "artifact_id": "chapter-one-artifact-uuid",
      "section_id": "chapter-one-uuid",
      "sha256": "64-hex-characters",
      "byte_size": 48200,
      "lesson_ids": ["lesson-one-uuid", "lesson-two-uuid"]
    },
    {
      "artifact_id": "chapter-two-artifact-uuid",
      "section_id": "chapter-two-uuid",
      "sha256": "another-64-hex-characters",
      "byte_size": 49900,
      "lesson_ids": ["lesson-three-uuid", "lesson-four-uuid"]
    }
  ]
}
```

Публичный каталог содержит метаданные Product/родителей/структуры и точные ссылки на учебные ревизии, но не вопросы закрытых уроков. Manifest полного пакета выдаётся по агрегированному полному праву; вместо постоянных URL в нём artifact ID. API доставки разрешает artifact только если он принадлежит доступной ревизии данного Product. Trial manifest сохраняется в PublishedRevision как immutable состав разрешённых уроков. После подтверждённого завершения пробы он позволяет серверу выдать SRS **только для её слов**, без полного entitlement; SRS не раскрывает вопросы закрытых уроков.

### Согласованная публикация каталога и PostgreSQL

`CatalogRevision` — один неизменяемый публичный снимок. Его UUID записан **внутри файла** как catalog_revision; SHA-256 считается по окончательным байтам UTF-8. PostgreSQL хранит те же данные в snapshot JSON и отдельно URL/object_key, hash и byte_size. Источник публичной актуальности — единственная строка CatalogHead с FK на **полностью подготовленный** CatalogRevision. `source_revision` этой строки — внутренний счётчик изменений входных данных, не публичный номер каталога.

Шаги публикации:

1. В короткой транзакции согласованно скопировать активный каталог, source_revision и выбранные к публикации черновики/редакционные изменения. Все изменения входных данных через сервисы Admin/import увеличивают source_revision в своей транзакции с блокировкой CatalogHead. Неподтверждённые черновики других материалов не попадают в снимок. Проверить полноту **всей** публикуемой книги/сезона/фильма и составить diff.
2. Вне транзакции сериализовать immutable учебные документы, загрузить в правильное пространство storage и проверить размер/hash. Собрать full/trial manifests. Trial: первая глава книги, первый эпизод только первого сезона, первые три урока фильма, исключительно при явном включении автором.
3. Построить кандидат каталога из активного снимка и только утверждённого diff: метаданные/авторы ru/en, производные серии, цены/режимы, структура и точные учебные ревизии. Никакого чтения изменяемых полей Admin при последующей выдаче этого снимка.
4. Загрузить **сам файл каталога** по новому immutable key вида `catalog/<revision-id>.json`. Проверить чтение по тому публичному пути, который получит клиент, и совпадение размера/hash. Учебные артефакты и указанные ресурсы должны уже существовать; отсутствующая обложка задаётся null, а не неработающим URL. Пока это подготовка, публичный head не меняется.
5. В одной короткой транзакции заблокировать CatalogHead, затем затронутые Product. Проверить прежний active head, source_revision и hashes черновиков. При совпадении создать PublishedRevision/PackArtifact (если меняется учебный контент), стабильные индексы, CatalogRevision со снимком и descriptor файла; переключить Product.current_revision и CatalogHead.current_revision. Время активации записать в PublishedRevision.published_at и PublicationEvent.occurred_at; Product.first_published_at заполняется только при первой публикации. Для одной правки каталожных метаданных событие новых уроков не создаётся. Commit делает всё это публичным одновременно. При изменившемся входе отменить активацию и перестроить кандидат, не затирая параллельные изменения.
6. `/catalog/head` одним чтением связанной активной строки возвращает согласованный набор catalog_revision/schema_version/url/sha256/byte_size. Не возвращать source_revision, максимальный номер подготовленного файла или «последний загруженный» объект. До commit виден весь старый набор, после — весь новый. Начальный запуск либо активирует готовый пустой каталог, либо отдаёт 503 `catalog_not_ready` без URL.

Метаданные/цены/режимы и авторы выпускаются тем же протоколом, но без перегенерации неизменённых упражнений. Публикация небольшого каталога синхронна в Admin; отдельный брокер/worker не нужен. Потерянный ответ Admin после успешного commit разрешается сверкой active head, а не слепой повторной публикацией того же diff.

GET `/catalog/products/{id}` и manifest с `catalog_revision=R` используют именно снимок R и указанный им content revision. Без параметра используется активный снимок с указанием его ID в ответе. Историческая ссылка не обходит текущий entitlement или юридическую блокировку; отключённая проба не выдаётся заново как актуальная. Цена заказа и claim-free всегда проверяются по **текущему активному** каталогу, а не по R телефона. Публичный snapshot может быть старым, но внутри себя он целостен.

Сбои и конкуренция:

- Ошибка подготовки/загрузки/проверки или rollback БД оставляет прежний head и прежнюю публичную версию материала. Готовые, но неактивированные объекты — безопасные orphan, не новые версии API.
- Два издателя не смешивают данные: первый commit меняет head, второй обнаруживает несовпадение и пересобирает кандидат. Дополнительная распределённая блокировка не требуется.
- Не перезаписывать объекты и не использовать URL `latest.json`; старые активированные файлы сохраняются. CDN может кэшировать immutable файлы надолго, но head требует revalidation. Ошибка storage после активации остаётся эксплуатационным риском: клиент сохраняет старый рабочий снимок и повторяет загрузку, а сервер не обещает распределённую транзакцию с Object Storage.
- Availability при юридическом снятии применяется сразу независимо от старого каталога. Затем публикуется снимок без материала/с блокировкой; уже скачанные копии и public trial URL мгновенно отозвать нельзя.

Предлагается хранить опубликованные артефакты MVP без автоматического удаления: они нужны для отложенного sync, жалоб и уже выданных SRS-вопросов. Это технический retention, без UI произвольного отката. Его стоимость контролируется; сокращение retention позднее потребует отдельного правила совместимости.

## 7. Атомарное обновление на устройстве

1. Получить catalog head; скачать файл именно по его URL, проверить размер/hash/schema и встроенный catalog_revision. Только после проверки всего снимка заменить локальный каталог одной SQLite-транзакцией. При ошибке оставить старый целостный каталог, не смешивать его поля с новым head. Затем запросить manifests с catalog_revision этого снимка, запланировать все обложки, включённые пробы и полные пакеты по агрегированным правам. Бесплатный полный пакет скачивается после явного добавления в библиотеку.
2. Скачать документы новой ревизии во временную область; проверить размер, SHA-256 и схему. SHA-256 защищает от повреждения, а доверие к manifest обеспечивает HTTPS API, не сам хеш.
3. Одной SQLite-транзакцией записать документы, индексы и manifest как `ready`. Активная старая ревизия пока сохраняется. Общие неизменённые документы можно переиспользовать.
4. Если урок этого Product активен, оставить его закреплённую ревизию до выхода/завершения. Затем одним commit переключить `active_revision_id` и пересчитать производную завершённость. Текущее завершение содержит ID закреплённой старой ревизии.
5. Если приложение закрылось, незавершённый урок при новом старте начинается с первого вопроса; можно активировать ready-ревизию до его запуска. Пройденный урок не показывает поздравление повторно.
6. После успешного переключения старую локальную ревизию можно автоматически освободить, когда на неё не ссылаются текущий урок и локальные отправляемые отчёты/операции. Сервер сохраняет её ID и снимок; прогресс хранится отдельно и не удаляется. Это внутренняя уборка заменённых версий, не UI удаления скачанного материала.

Изображения сначала записываются в постоянный файл с content hash, затем путь фиксируется в SQLite; оборванный временный файл не становится активным. Для JSON одна транзакция SQLite избегает двухфазного commit между БД и файлами. Ошибка диска/сети/схемы оставляет старую версию, показывает состояние проблемы и запускает безопасный повтор.

Первоначальная подготовка имеет сохраняемый checklist и повторяет только недостающие элементы. После подготовки открывается «Моя библиотека». Предлагается разрешать уже скачанные материалы при частичной ошибке обложки с типографической заглушкой; ошибка нужного учебного пакета явно видна. Точное условие завершения экрана подготовки выделено в рисках.
