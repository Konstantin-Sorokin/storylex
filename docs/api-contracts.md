# Storylex: REST API v1

Статус: предлагаемые контракты, не реализованный API. Детали алгоритмов — в [sync и SRS](sync-and-srs.md).

## 1. Общие правила

- Базовый путь `/api/v1/`, HTTPS, JSON UTF-8, UUID в строках, даты RFC 3339 в UTC. День SRS — 24 часа; локальная дата/время только для отображения и напоминаний.
- Приватные запросы: `Authorization: Bearer <access_token>`. Пользователь определяется сеансом, не полем `user_id` из JSON. Device ID не заменяет авторизацию.
- Версия API и версия учебной схемы независимы. Изменения v1 по возможности аддитивны; обязательное изменение смысла требует новой версии.
- Пагинация списков: `limit` (по умолчанию 50, максимум 100), непрозрачный `next_cursor`; sync — отдельный курсор, до 500 изменений на страницу. Упорядочивание всегда устойчивое, с ID как последним ключом.
- GET каталога/manifest: ETag и `If-None-Match`, ответ 304. Персональные документы не кэшируются общим CDN. Подписанные URL не входят в долговечный каталог.
- Предлагаемые таймауты клиента: 15 секунд для обычного API, 60 секунд бездействия для загрузки документа; сеть/5xx — exponential backoff с jitter от 1 секунды до 5 минут. 429 учитывает `Retry-After`. POST повторяется только с тем же operation/idempotency key. После 401 — одна попытка refresh, затем явное восстановление входа без удаления локальной очереди.
- Ошибки: 400 invalid input; 401 session required; 403 no entitlement/staff; 404 неизвестный/недоступный объект; 409 revision/idempotency conflict; 410 истёкший challenge; 413 размер; 422 неподдерживаемая схема; 429 rate limit; 5xx временный сбой. Для batch sync конфликты конкретных операций передаются в теле 200, общий невалидный envelope отклоняется целиком.

```json
{
  "error": {
    "code": "bookmark_revision_conflict",
    "message": "Словарь изменился на другом устройстве",
    "details": { "item_id": "uuid", "current_revision": 12 },
    "request_id": "uuid"
  }
}
```

`code` стабилен, клиент локализует сообщения. В ответах нет stack trace, секретов и полных платёжных payload. Ниже UUID сокращены до `uuid` для читаемости; это примеры формы, не готовые fixtures.

## 2. Авторизация и профиль

| Метод и путь | Запрос | Результат |
|---|---|---|
| `POST /auth/attempts` | provider google/yandex; purpose login/link; callback из allowlist; challenge устройства для возврата | attempt_id, authorization_url, expires_at; для link нужна действующая сессия |
| `GET /auth/callback/{provider}` | code/state от провайдера | Сервер проверяет попытку, обменивает code, возвращает в приложение одноразовый ticket, не access token в URL |
| `POST /auth/exchange` | ticket + доказательство verifier устройства + device_id | user, session_id, access_token, refresh_token, expires_in |
| `POST /auth/refresh` | refresh_token, request_id | Ротация refresh, новый access; повтор того же запроса должен безопасно восстановить ответ в коротком окне |
| `POST /auth/logout` | session_id текущего сеанса | Отзыв серверного сеанса; клиент очищает доступную сессию и закрывает личную БД |
| `GET /me` | — | Минимальный профиль, связанные провайдеры, настройки, их ревизия |
| `DELETE /me/identities/{id}` | Недавнее подтверждение входа | Отвязка, если остаётся минимум один способ входа |
| `PATCH /me/settings` | expected_revision + изменённые поля | Настройки и новая ревизия; при устаревании 409 |
| `DELETE /me` | Явное подтверждение, недавняя повторная авторизация | Удаление/обезличивание по утверждённой политике, отзыв сеансов |

Одинаковая серверная граница проверки identity применяется для входа и привязки. Конкретный OAuth flow Google и Яндекс проверяется отдельным ранним spike, см. [безопасность](security-and-risks.md): не предполагается, что оба провайдера поддерживают одинаковые параметры или что Expo Go достаточен.

## 3. Каталог, права и загрузки

| Метод и путь | Результат / проверка |
|---|---|
| `GET /catalog/head` | Descriptor только активного и уже подготовленного CatalogRevision: ID, schema_version, URL, sha256, byte_size; не редакционная source_revision |
| `GET /catalog/products/{id}?catalog_revision=R` | Метаданные/структура из снимка R без закрытых упражнений; без R — активный снимок; ответ содержит catalog_revision |
| `GET /me/entitlements` | По одной агрегированной записи на Product, включая утрату полного права; не по одной записи на источник покупки/free |
| `POST /products/{id}/claim-free` | Пустой body + Idempotency-Key; по актуальному активному каталогу проверить free, создать единственное free-основание или вернуть его; покупное основание не заменять |
| `GET /products/{id}/manifest?scope=trial\|full&catalog_revision=R` | Учебная ревизия из R (без R — активного снимка); full требует хотя бы одного действующего основания, новые пробы — актуального разрешения trial |
| `POST /content/downloads` | artifact_ids актуального/разрешённого manifest; сервер проверяет каждый ID; возвращает краткоживущие подписанные GET URL |
| `GET /dev/products/...` | Только staff, только окружение preview/dev; публичная сборка маршруты не использует |

### Атомарный head и чтение снимка

```json
{
  "catalog_revision": "catalog-revision-uuid",
  "schema_version": 1,
  "url": "https://public-storage.example/catalog/catalog-revision-uuid.json",
  "sha256": "64-hex-characters",
  "byte_size": 48200
}
```

Все поля берутся из одного CatalogRevision через активный FK CatalogHead. Файл с этим ID и hash готов и проверен **до** переключения FK. `/catalog/head` использует `Cache-Control: no-cache`, ETag активного снимка и `If-None-Match`; 304 не является сигналом перечитывать изменяемые поля Product. Если ещё нет готового каталога — 503 `catalog_not_ready` без descriptor. Файлы снимков immutable, допускают долгий публичный cache; URL `latest.json` не используется.

Клиент проверяет hash/размер/версию схемы/встроенный catalog_revision, после чего одной транзакцией заменяет локальный каталог. До этого активен прежний снимок. Сопутствующие запросы с R сохраняют согласованность метаданных/состава, даже если head сменился во время загрузки. Текущие ограничения availability и полного доступа проверяются отдельно. Заказ и claim-free никогда не доверяют цене или бесплатности старого R. Протокол активации и отказов — в [публикации](content-format.md).

Книга в каталоге содержит `year` и `author: {id, name_ru, name_en}`. Карточка книжной серии содержит `authors` (уникальные авторы опубликованных томов) и `year` (минимальный год выхода этих томов). Это производные одного снимка, без собственного редактируемого автора/года серии. Оба имени автора включаются в локальный поиск при любой локали; отдельный серверный поиск/новые фильтры не добавляются.

### Итоговое право и доступ к пробе

Пример агрегата `/me/entitlements` и соответствующего состояния UserChange (не список платёжных оснований):

```json
{
  "product_id": "product-uuid",
  "has_full_access": true,
  "granted_at": "2026-11-10T12:00:00Z",
  "revision": 52
}
```

`has_full_access` вычисляется по любому неотозванному основанию; `granted_at` — самое раннее действующее, либо null при их отсутствии. Availability проверяется дополнительно: это поле каталога/оперативный серверный запрет, оно не смешивается с персональной revision. Revision — номер последнего изменения агрегата в UserChange, не catalog_revision. Полный возврат одного заказа оставляет has_full_access=true при наличии free/другого основания. Новое состояние попадает в sync даже при неизменном итоговом true. Повтор claim-free не плодит основания; при уже существующем платном основании отдельное free всё равно сохраняется, если материал сейчас бесплатный и нет исключительного запрета.

Указание произвольного object_key клиентом запрещено. Бесплатный Product не выдаёт full-пакет автоматически всем: сначала явное добавление и персональное право. Trial не создаёт полный entitlement и библиотечную запись. **Слова завершённого пробного урока разрешено вручную добавлять в словарь и повторять через онлайн-SRS без покупки.** Для этого сервер подтверждает completion и сохраняет trial_revision; после обычного offline-sync дополнительных действий от пользователя не требуется. Этого разрешения недостаточно для полного manifest, закрытых упражнений или уведомлений о приобретённых материалах.

```json
{
  "downloads": [
    {
      "artifact_id": "uuid",
      "url": "https://private-storage.example/signed-get",
      "expires_at": "2026-11-10T12:05:00Z",
      "sha256": "64-hex-characters",
      "byte_size": 48200
    }
  ]
}
```

Предлагаемый TTL URL — 5 минут. Истёкший URL запрашивается заново с повторной проверкой права; не менять текущий рабочий пакет из-за этой ошибки.

## 4. Подтверждённое состояние и отправка outbox

| Метод и путь | Смысл |
|---|---|
| `GET /sync/changes?after=<cursor>&limit=500` | Неизменяемые изменения аккаунта, `next_cursor`, `has_more`, `through_cursor`; при первом входе after=0 |
| `POST /sync/operations` | До 100 операций, не более 256 KiB; device_id + упорядоченные операции; индивидуальные квитанции |

Пример отправки:

```json
{
  "device_id": "uuid",
  "operations": [
    {
      "operation_id": "uuid-completion",
      "sequence": 21,
      "type": "lesson.complete",
      "occurred_at": "2026-11-10T11:00:00Z",
      "payload": {
        "product_id": "uuid",
        "lesson_id": "uuid",
        "content_revision_id": "uuid"
      }
    },
    {
      "operation_id": "uuid-bookmark",
      "sequence": 22,
      "type": "bookmark.set",
      "occurred_at": "2026-11-10T11:01:00Z",
      "payload": {
        "item_id": "uuid",
        "content_revision_id": "uuid",
        "present": true,
        "base": { "revision": 0 },
        "expected_generation": null,
        "confirm_reset": null
      }
    }
  ]
}
```

`base` — либо `{revision: N}`, либо `{operation_id: <предыдущая операция того же item>}`. `expected_generation` — UUID/null либо `{from_operation_id: <предыдущая операция>}`, если generation ещё не присвоена сервером; ссылка обязана вести на успешный результат того же item/аккаунта/устройства. Для удаления `present=false`; при подтверждённом удалении истории `confirm_reset` содержит generation и srs_revision, показанные при подтверждении. Правила — в [sync](sync-and-srs.md).

```json
{
  "results": [
    {
      "operation_id": "uuid-completion",
      "status": "applied",
      "state": { "lesson_id": "uuid", "completed": true },
      "change_revision": 41
    },
    {
      "operation_id": "uuid-bookmark",
      "status": "conflict",
      "code": "bookmark_revision_conflict",
      "state": {
        "item_id": "uuid", "present": false,
        "revision": 9, "generation": null
      }
    }
  ],
  "server_time": "2026-11-10T12:00:00Z"
}
```

Статусы: `applied`, `noop`, `conflict`, `needs_confirmation`, `blocked_by_conflict`, `rejected`. Повтор того же ID/того же payload возвращает сохранённую квитанцию; это не новая мутация. Тот же ID с другим payload — `idempotency_key_reused`, без обработки изменённой команды. Временная ошибка/timeout без квитанции оставляет операцию pending. `last_successful_sync` обновляется только после отправки доступной очереди и полного pull до `through_cursor`, а не после одиночного успешного HTTP.

Пример страницы изменений:

```json
{
  "changes": [
    {
      "cursor": "41",
      "entity": "lesson_completion",
      "id": "uuid",
      "state": { "lesson_id": "uuid", "completed": true }
    }
  ],
  "next_cursor": "41",
  "through_cursor": "48",
  "has_more": true
}
```

Курсор не заменяется `change_revision` из POST: до него могли быть изменения другого устройства. Завершение списка pull гарантирует обработку всех промежуточных изменений. Начальная загрузка через after=0 восстанавливает права, завершения и словарь; SRS-история отдельным офлайн-снимком не переносится, актуальное состояние получает онлайн-API.

Состояние lesson_completion дополнительно содержит `trial_revision` (UUID/null). При принятии lesson.complete сервер сам проверяет trial manifest указанной content_revision_id и при необходимости заполняет это поле, даже если сам урок уже завершён. Клиент не присылает доверенный `is_trial`. Перед добавлением пробных слов на сервер сначала доставляется соответствующее завершение урока; перед SRS — завершения и ожидающие закладки. Синхронизация такого завершения/закладки не требует full Entitlement.

## 5. Серверные повторения

| Метод и путь | Вход / результат |
|---|---|
| `GET /srs/summary` | ready_count, saved_count, nearest_review_at, calculated_at |
| `POST /srs/queue` | limit ≤10; exclude_challenge_ids текущей очереди; до 10 уникальных слов со сроком; при остатке 2 клиент задаёт limit=8 |
| `POST /srs/answers` | answer_id, challenge_id, selected_option_id; правильность, новый срок/уровень и актуальная summary |
| `GET /dictionary?cursor=...` | Состояние словаря с bookmark revision/generation и текущим has_history/srs_revision; для онлайн-экранов и восстановления после конфликта |

Выдаваемый challenge содержит item, prompt, четыре options с серверной перестановкой, exercise type, expires_at и revision контента. **Не содержит correct_option_id.** Ответ на обычный вопрос проверяется из JSON, ответ SRS — только сервером.

Единая проверка для summary/queue/answer: present-закладка и (действующее полное право **или** подтверждённое завершение её пробного урока с trial_revision); глобальная юридическая блокировка запрещает обе ветки. Без полного права вопрос берётся только из сохранённого пробного снимка. Отключение новой пробы/возврат покупки сами по себе не стирают это основание и историю SRS. Отсутствие full Entitlement не является 403 для такого пробного слова, а наличие пробного слова не разрешает SRS закрытых слов.

```json
{
  "answer_id": "uuid",
  "challenge_id": "uuid",
  "selected_option_id": "uuid"
}
```

Устаревшая generation/state revision, удаление слова или ответ на другом устройстве дают 409/410 и актуальное состояние без второго изменения интервала. После потери ответа повторяется тот же answer_id онлайн; офлайн-очередь ответов не создаётся. При рестарте клиент просто получает актуальную очередь.

## 6. Оплата

| Метод и путь | Поведение |
|---|---|
| `POST /orders` | product_id, Idempotency-Key; серверная цена; создаёт или возвращает активный заказ/уже имеющееся право |
| `GET /orders/{id}` | Только владелец; status pending/succeeded/failed/canceled/refunded, confirmation_url при необходимости, entitlement |
| `POST /orders/{id}/refresh` | Идемпотентная сверка с провайдером при возврате в приложение; ограничение частоты |
| `POST /payments/yookassa/webhook` | Без пользовательского Bearer, но с проверкой объекта у провайдера; durable processing + дедупликация |

Мобильный клиент автоматически проверяет заказ при возврате, далее короткий ограниченный polling с backoff, пока платёж в обработке. Нельзя выдать entitlement по deep link `success`. Итоговые названия/набор платёжных статусов и способ открытия оплаты утверждаются после коммерческой проверки схемы RuStore/ЮKassa.

Каждый проверенный успешный заказ создаёт не более одного purchase-основания, привязанного к order. Подтверждённый полный возврат отзывает только его, после чего пересчитывается агрегированное право; повторные/поздние уведомления не создают новое основание и не отменяют refund. Несколько оснований не создают несколько записей `/me/entitlements`. При наличии действующего полного права новый заказ не создаётся, но уже проведённый платёж сверяется независимо от параллельного получения free.

## 7. Жалобы, уведомления, удаление

| Метод и путь | Поведение |
|---|---|
| `POST /reports` | report_id, content/revision/lesson/exercise IDs, comment; повторяемый запрос; офлайн outbox отдельного типа |
| `GET /reports/{id}` | Только своя жалоба, статус отправки/приёма; нет публичного списка жалоб |
| `GET /notifications` | История, unread_count, курсор прочтения последнего возвращённого события |
| `POST /notifications/read` | read_through_cursor; отметить открытый список, не будущие сообщения |

Жалоба принимает ссылку на историческую опубликованную ревизию. Для SRS challenge сервер восстанавливает снимок сам. Клиент не присылает токены/полные книги в комментарии автоматически. Отправка жалобы не блокирует учебный sync. Удаление аккаунта не может выполняться отложенной офлайн-командой; нужен подтверждённый онлайн-сеанс.
