# Мобильный клиент: этапы 1.3–1.4

Реализованы Expo/TypeScript, четыре базовых раздела, локальный каталог,
экран произведения и список уроков главы. Подготовка читает опубликованные
trial manifest и пакеты из Django 1.2. В 1.4 добавлены [прохождение уроков,
локальные dev-результаты и короткое повторение](lesson-development.md).
Библиотека пуста, проба её не пополняет. Sync остаётся в 1.5.

## Запуск

Нужен Node **24.13+** (проверено 24.19.0), npm и Android с Expo Go,
совместимым с SDK **58**, либо Android development build. Metro/Android export
и SQLite через Node проверены автоматически; владелец также проверил приложение
на реальном Android через Expo Go (12.11.2026).

1. Запустите PostgreSQL и Django по [README](../README.md).
2. В Admin подготовьте короткую полностью готовую dev-книгу, включите
   `trial_enabled`, импортируйте главу и опубликуйте **весь** Product по
   [инструкции автора](content-authoring.md). Одного сохранения черновика мало.
   Для существующего JSON используйте реальные UUID выбранных Product/Section.
   Не включайте пробу настоящей книги только ради теста без решения автора.
3. Из корня:

```bash
cd mobile
npm ci
cp .env.example .env
npm start
```

Не перезаписывайте существующий `.env`. `EXPO_PUBLIC_API_URL` содержит только
адрес, **никогда не секреты**. Для стандартного Android Emulator:
`http://10.0.2.2:8000/api/v1/`. При USB/adb можно использовать
`adb reverse tcp:8000 tcp:8000` и адрес `http://127.0.0.1:8000/api/v1/`.
Наличие adb и эти два варианта соединения здесь не проверялись.
Для телефона в LAN укажите доступный ему адрес хоста; локальный Django запускайте
на `0.0.0.0:8000` и добавьте фактический host в `DJANGO_ALLOWED_HOSTS`.
Для WSL2 проверьте Windows firewall и доступность WSL-порта с устройства.
Это локальная разработка в доверенной сети, не production-развёртывание.
После изменения EXPO_PUBLIC_API_URL перезапустите Metro.

Первый запуск подготавливает каталог и включённые пробы, затем открывает
«Мою библиотеку». Каталог → произведение → «Открыть пробную главу» показывает
заголовок, число слов и список уроков из скачанного документа. Повтор подготовки:
Настройки → «Обновить материалы». Неполная загрузка не блокирует уже скачанные
главы; ошибка показана в настройках и на экране отсутствующего пакета.

## Хранение и проверки

`storylex-public-v1.db` в постоянном каталоге Expo SQLite хранит только публичный
каталог и пробы. Здесь нет аккаунтов, чужих полных пакетов или личного прогресса.
`PRAGMA user_version` управляет миграциями; неизвестная новая версия отклоняется
без сброса БД. WAL и foreign keys включены; отдельное соединение записи включает
foreign keys до BEGIN, чтобы экранные запросы не попадали внутрь транзакции.
В 1.4 используется постоянный сериализованный writer и отдельный reader для
каждой БД, synchronous=FULL. Content-миграция v2 добавляет ready_packages, сохраняя
кэш v1; отдельная learning-dev-БД хранит локальные результаты и не является
общим публичным хранилищем или аккаунтным прогрессом.

Каталог проверяется по schema/version, размеру UTF-8, SHA-256 и встроенной ревизии;
заменяется одной транзакцией. Manifest закреплён на catalog_revision, проверяются
product/revision/scope/engine/counts, состав первой главы и точные lesson IDs.
Документы проверяются общей source.schema.json и смысловыми проверками ссылок,
UUID/пяти единиц/трёх вопросов/вариантов. Сначала сохраняются проверенные blobs
по hash, затем одной транзакцией manifest, индексы и активный указатель. Сбой
оставляет старую главу; повтор использует уже проверенный blob. Незаконченная
подготовка не создаёт активный пакет. Старые версии пока автоматически не удаляются.

Обычный повторный запуск с сохранённым каталогом **не делает HTTP-запросов**.
Навигация читает SQLite. Обновление сейчас явное; pin активного урока и ready
реализованы в 1.4. Фоновое обновление, полная подготовка с обложками и автоматическое
восстановление сети относятся к следующим этапам. Trial-документы не создают
библиотеку/entitlement; локальный dev-результат создаётся только после прохождения.

## Автоматические проверки

Из `mobile`:

```bash
npm test
npm run typecheck
npx expo install --check
npm run export:android
```

Тесты — встроенный `node:test` и настоящая SQLite через `node:sqlite`, без нового
тестового фреймворка. `--test-isolation=none` явно запускает TS-тесты в одном
процессе; проверяются отдельные сценарии, а не только загрузка файлов тестов.
Отдельный live-backend тест в npm test пропускается без STORYLEX_TEST_API_URL.

Полный Django test runner после `npm ci` автоматически запускает его со своим
LiveServer, отдельной PostgreSQL и временным storage: импорт → публикация → HTTP →
клиентская проверка → SQLite → закрытие/повторное открытие. Рабочий каталог не
меняется. Без Node/установленных мобильных зависимостей этот сквозной тест явно
пропускается; остальные Django-тесты не зависят от npm.

Проверено 10.11.2026: чистый `npm ci`, **87 Django-тестов** на PostgreSQL,
включая выполненный cross-stack LiveServer тест; **11 клиентских тестов**
и 1 ожидаемый skip live-теста при отдельном npm test; TypeScript strict,
совместимость модулей Expo, конфигурация Expo и Android JS/Hermes export.
`manage.py check --database default`, `makemigrations --check --dry-run`
и `git diff --check` прошли. Серверные миграции не требовались.

## Ручная проверка

12.11.2026 владелец подтвердил успешную проверку на реальном Android через Expo Go:
подключение к Django API, загрузку опубликованного каталога, открытие и сохранение
пробной главы, повторное открытие главы из SQLite при отключённых Django и интернете
и восстановление работы каталога после возвращения соединения. Этап 1.3 принят;
на момент этой приёмки этап 1.4 ещё не был начат. 13.11.2026 владелец отдельно
принял runner 1.4 после ручной проверки Android; точный объём приёмки,
автоматическая проверка выхода и ограничения — в [инструкции 1.4](lesson-development.md).

1. Подготовьте опубликованную пробу и откройте главу из каталога. Сверьте заголовок,
   число уроков и пять единиц на урок с JSON, опубликованным в Admin.
2. Закройте приложение полностью и остановите **Django**. Откройте приложение снова,
   каталог, произведение и ту же главу. Они должны работать без запросов к Django;
   проверьте его access log при обычной навигации. Expo Go может отдельно требовать
   доступ к Metro для самого JS bundle — это не запрос учебного контента.
3. Нажмите обновление при отключённом Django: получите ошибку, прежняя глава доступна.
   Запустите Django и повторите: ошибок нет, повторных локальных уроков нет.
4. Исправьте JSON, сохраняя UUID, импортируйте без публикации: клиент ещё получает
   старый снимок. Опубликуйте, обновите материалы: новая глава появляется целиком.
5. Проверьте четыре вкладки, возврат Android Back, тёмную тему и увеличенный
   системный шрифт. Полный авиарежим с убийством native-процесса проверять на сборке
   с доступным JS bundle; этот сценарий здесь автоматически не выполнялся.

## Зависимости и ограничения

Версии фиксирует `mobile/package-lock.json`. Expo/React Native/React/TypeScript —
утверждённый стек; Router и screens/safe-area/linking/constants — файловая навигация
и её peer dependencies, status-bar — совместимый peer Router. Альтернатива — ручная
навигация и управление Android Back, что увеличивает собственный код. React DOM
закреплён на версии React для согласованных peers Router; web-приложение не добавлено.
`expo-sqlite` предоставляет постоянную SQLite; JS-память/AsyncStorage не заменяют
транзакции. `expo-crypto` проверяет SHA-256 штатным модулем Expo вместо собственной
криптографии. `ajv` выполняет общие JSON Schema Draft 2020-12; альтернатива — ручные
валидаторы с риском расхождения с Django. `@types/node` нужны только для тестов.
Поддержка: обновлять SDK и его модули совместно, lockfile и контрактные тесты;
отдельных ORM, state framework, HTTP-клиента и тестовых драйверов нет.
Документация: [Expo SQLite](https://docs.expo.dev/versions/v58.0.0/sdk/sqlite/),
[Expo Crypto](https://docs.expo.dev/versions/v58.0.0/sdk/crypto/).

В этом этапе нет OAuth/dev-auth endpoint, тестовых полных прав, платного контента,
поиска/группировки полного каталога, обложек, локализации ru/en UI,
outbox/sync, SRS и оплаты. Lesson runner добавлен в 1.4. Каркас доступен только при `__DEV__`; production bundle
показывает экран недоступности, без обхода авторизации. Публичный релиз запрещён.

`npm audit` обнаружил **5 moderate** в цепочке Expo CLI/fingerprint → glob/minimatch,
без high/critical. Предложенный npm автоматический fix требует смены major Expo;
он не применялся. Это известное ограничение toolchain, а не пройденный security gate.
Web/iOS и отдельная Android APK/development build не проверены. Ручная проверка
Expo Go описана выше; полный авиарежим с убийством native-процесса и недоступным
Metro отдельно не подтверждён. Воспроизводимый Android JS/Hermes export не заменяет
APK и native-тест.
