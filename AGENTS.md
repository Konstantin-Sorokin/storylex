# Инструкции для ИИ-агентов Storylex

Storylex — мобильное приложение для изучения английского по книгам, фильмам и сериалам. Это не ридер, видеоплеер или общий курс. Проект поддерживает один разработчик: предпочитай простые, понятные и проверяемые решения.

## Структура и стек

Целевая структура монорепозитория (каталоги приложений пока не созданы):

- `docs/` — требования, архитектура, контракты и этапы.
- `backend/` — Python, Django, DRF, PostgreSQL; зависимости через uv.
- `mobile/` — React Native, Expo, TypeScript, SQLite; Android/RuStore первыми.
- `contracts/` — учебные JSON Schema, OpenAPI и общие примеры.
- `infra/` — Docker Compose и конфигурация развёртывания.

Backend — один модульный Django-монолит; Django Admin — CMS. Не вводи микросервисы, брокеры, дополнительные хранилища или универсальные слои ради гипотетического роста. Новые функции вне ТЗ и изменения принятых решений сначала согласуй с владельцем. Зависимость добавляй только для конкретной задачи разрешённого этапа: объясни необходимость, альтернативу средствами текущего стека и стоимость поддержки; зафиксируй lockfile.

## Качество кода

- Python: соблюдай PEP 8, используй понятные имена, небольшие функции и аннотации типов на границах модулей. Обрабатывай ожидаемые ошибки явно, не скрывай сбои широкими `except`.
- Django/DRF: модели и ограничения защищают целостность; сервисы задают бизнес-операции и транзакции; views/serializers отвечают за HTTP и валидацию. Используй ORM напрямую, избегай N+1. Не прячь критические переходы в цепочках signals и не держи транзакцию во время внешнего HTTP.
- TypeScript: строгая типизация, явные типы контрактов и состояний; избегай `any` и необоснованных type assertions. Проверяй внешние JSON во время выполнения: TypeScript не валидирует сетевые данные.
- React Native: небольшие компоненты и hooks; предметная логика, HTTP и SQLite отделены от экранов. Не дублируй постоянное состояние SQLite целиком в JS store. Учитывай ru/en, темы, масштаб текста и длинные варианты ответов; упражнения всегда EN↔RU.
- Сохраняй стиль существующего кода. Не добавляй абстракции, инструменты и массовые рефакторинги без необходимости для текущей задачи.

## Совместимость и обязательные инварианты

- Сохраняй совместимость API, JSON-схем и скачанных пакетов. Несовместимое изменение требует явного версионирования и согласованного перехода; стабильные ID уроков/слов не зависят от текста или порядка.
- Не удаляй пользовательский прогресс при переимпорте, обновлении или конфликте. Завершение урока и outbox записываются одной SQLite-транзакцией до итогов; доставка идемпотентна. Завершения объединяются, словарь использует CAS/generation, SRS рассчитывается только сервером онлайн.
- Пакеты immutable; обновление атомарно и не подменяет текущий урок. Файл каталога готов и проверен до атомарной активации CatalogHead. Подробности — в документах, не изобретай альтернативный протокол.
- Product/Section — общие сущности контента. Одинаковые слова разных произведений имеют независимые ID/истории. Слова завершённой пробы доступны для словаря/SRS без покупки, но не дают полного права или записи библиотеки.
- Entitlement хранит отдельные основания: возврат отзывает только основание своего заказа. Итоговое право агрегируется без дублей библиотеки. Изолируй данные аккаунтов; проверяй приватный доступ на сервере; не публикуй платные пакеты и не записывай секреты/токены в Git или логи.

## Проверки и миграции

- Для изменений поведения добавляй содержательные тесты: правила предметной области, ошибки, ограничения доступа и совместимость. Критические сценарии sync, публикации, SRS и платежей проверяй также на повторах, сбоях и конкуренции; критерии находятся в ТЗ и плане.
- Изменения схем PostgreSQL и SQLite сопровождай миграциями в рамках разрешённой задачи. Проверяй чистое создание и обновление существующих данных; не редактируй уже применённые миграции и не сбрасывай БД/прогресс ради прохождения проверок.
- Запускай проверки затронутой области и существующие проверки типов/стиля, когда они появятся. Сейчас команды запуска и тестирования не определены: не придумывай их. Документируй только реально настроенные и проверенные команды после создания приложений.
- Перед сдачей проверь diff, связанные контракты и документацию; не затрагивай посторонние изменения владельца. В отчёте укажи результат, выполненные проверки, что не проверено и известные ограничения. Не утверждай, что непроведённые проверки прошли.

## Разрешение на этапы

Выполняй только явно разрешённый этап/подэтап из плана. Не переходи к следующему без разрешения владельца, даже если проверки прошли. Согласование архитектуры или этих инструкций не разрешает реализацию, установку зависимостей или создание проектов. Этап 1.1 также требует отдельного явного разрешения.
